# 项目 15 模块 B 报价刷新需求

## Financial News & Portfolio Impact Service

> 版本 v1.0 ｜ 2026-07-28
> 前置文档：`项目15-②架构设计.md` §4.2、§5、§6.5、§7.1｜`项目15-⑤实体使用说明.md`
> 对应需求：B1、B4（采集侧）｜边界条件 EC-11、EC-12、EC-13、EC-20、EC-23
> 负责人：模块 B

本文档只讲**一个定时任务**：每分钟刷新报价，把结果写进 `price_quote` 和 `price_point`。
范围刻意开得小，因为它是当前唯一有时效性的后端任务 —— 见第 1 节。

估值计算（B2/B3）、收盘快照（B5）、读接口都不在本文档内，第 11 节列了边界。

---

## 1. 为什么这个任务不能等

`price_point` 表（V7）是联动视图曲线的唯一数据来源。契约里 `impact-view`
返回的 `priceSeries.points` 是分钟级的时间序列：

```json
"priceSeries": {
  "newsMarker": "2026-07-27T12:31:00Z",
  "points": [
    { "t": "2026-07-27T12:00:00Z", "price": "121.85" },
    { "t": "2026-07-27T12:31:00Z", "price": "121.90" },
    { "t": "2026-07-27T12:35:00Z", "price": "125.60" }
  ]
}
```

现有两张表都给不出这个：`price_quote` 每个代码只有一行且被覆盖，
`price_bar` 每个交易日只有一个收盘价。

**关键在于这些行补不回来。** 免费数据源不出售历史分钟线，
所以没有采集的那一天，曲线永久缺失。`price_bar` 缺了还有架构 §6.3 的报价兜底方案，
`price_point` 一点兜底都没有。

架构 §5 已经写明「报价刷新那条的『追加 price_point』不是可选项」。
表已经建好了，但**建表不等于在采集** —— 往里写行的是这个任务。

优先级判断：这条曲线是演示脚本第 4 步的核心画面。
每过一天不跑，演示能覆盖的时间窗就少一天。

## 4. `PriceProvider` 接口：一个要先定的取舍

架构 §决策1 里接口是这样写的：

```java
public interface PriceProvider {
    Optional<PriceQuote> fetchQuote(String symbol);
    List<PriceBar> fetchDailyBars(String symbol, LocalDate from, LocalDate to);
}
```

**问题：`PriceQuote` 和 `PriceBar` 都是 `@Entity`。**

让集成层返回实体，有几个地方会变得含糊：Finnhub 的实现该不该填 `@Id`、
返回的对象是 detached 还是 transient、service 拿到之后能不能直接 `save`。
更根本的是方向问题 —— §7.1 要求「Finnhub 的字段名不许泄漏到业务层」，
初衷是隔离两侧；而让集成层构造持久化对象，是把耦合换了个方向而不是消除它。

**建议方案：** 接口返回不带 JPA 注解的 record，由 service 转成实体。

```java
// integration/QuoteSnapshot.java —— 不是 @Entity
public record QuoteSnapshot(
        String symbol,
        BigDecimal price,
        BigDecimal previousClose,   // 可能为 null，见 EC-19
        Instant capturedAt) {}

public interface PriceProvider {
    Optional<QuoteSnapshot> fetchQuote(String symbol);
}
```

好处是集成层只管「从外部拿到了什么」，持久化决策留在 service；
`MockPriceProvider` 也不用碰 JPA。

**这是对架构文档的偏离，需要显式处理：** 要么在 PR 描述里说明并回写 §决策1，
要么按原文返回实体。**这条由你和架构负责人定，本文档只陈述取舍，不替你决定。**

`fetchDailyBars` 属于 B5 收盘快照，本次不实现，但接口里先声明还是等 B5 再加，
一并在上面那个决定里定掉。

## 5. 限流与降级

**限流器已经配好了，直接用，不要新建。** `application.yml` 里：

```yaml
resilience4j:
  ratelimiter:
    instances:
      finnhubPrice:            # ← 用这个
        limit-for-period: 30
        limit-refresh-period: 60s
```

```java
@RateLimiter(name = "finnhubPrice")
@Retry(name = "externalApi")
@CircuitBreaker(name = "finnhub")
```

**绝对不要共用 `finnhubNews` 那个实例**（架构 §6.5 要求 1）。
共用的话新闻轮询会把限流器打满，顺带让报价刷新被拒 —— 那两个独立账号就白买了。
新闻被 429 时只该降级新闻这条链路。

**429 不重试。** `retry.instances.externalApi` 的配置注释已写明：
重试限流只会让限流更严重。

**失败处理：不要把异常抛给上层。** 单个 symbol 拉取失败时记日志并跳过，
继续处理下一个。读接口从库里出上一次的数据，配 `stale: true`
—— 这是架构决策 2 的核心，上游挂掉的结果是旧数据加标记，不是报错（EC-11、EC-12）。

**日志里不许出现 key。** URL 记成 `token=***`（架构 §7.5）。

**EC-13（停牌查不到价）：** provider 返回空，跳过这个 symbol，不要写入 0 或者 null 价格。
`price_quote` 里保留上次已知价 —— `PriceQuote` 实体注释里写了「survives a halt」就是这个意思。

## 6. 交易时段判断

**规则：US/Eastern 时间 09:30–16:00，周一至周五。** 时段外直接返回，不调 provider。

```java
private static final ZoneId MARKET_ZONE = ZoneId.of("America/New_York");
```

用 `America/New_York` 而不是服务器本地时区 —— 夏令时切换由时区库处理，
写死 UTC-5 每年会错两次。

**不做美股假日表。** 感恩节、圣诞、独立日这些当天，任务照常跑。

这是一个**已知偏差，团队接受**：假日当天约 390 次无效调用（6.5 小时 × 60），
浪费额度但不产生错误数据 —— provider 在休市日返回的是上一个交易日的收盘价，
写进 `price_point` 只是一串重复的点，不是错的点。
额度是 30 次/分钟，跑 15 只标的每分钟用 15 次，有余量。

要做的话就查一张 `MarketCalendar`，但那是后话，不阻塞本次交付。

**时段判断必须可测。** 别在方法里直接调 `Instant.now()`，
把当前时间作为参数传进去，否则第 9 节那三个单测写不了。

## 7. 并发与执行锁

**定时触发：**

```java
@Scheduled(fixedDelayString = "${app.schedule.quote-refresh-delay}")
```

配置项已存在，值 60000（1 分钟）。

**必须用 `fixedDelay`，不是 `fixedRate`。** `fixedDelay` 从上一轮结束开始计时，
所以任务永远不会和自己重叠 —— 这就解决了 EC-23，不需要额外加锁。
`fixedRate` 在 API 变慢时会让多轮堆在一起。

**手动触发需要显式锁。** 手动触发走的是 HTTP 线程，和定时任务不是同一条线程，
`fixedDelay` 管不到（EC-20）。用 `AtomicBoolean`：

```java
private final AtomicBoolean running = new AtomicBoolean(false);

public boolean tryRefresh() {
    if (!running.compareAndSet(false, true)) {
        return false;                   // 拿不到锁
    }
    try {
        doRefresh();
    } finally {
        running.set(false);             // finally 不能省，异常时也要放锁
    }
    return true;
}
```

**拿不到锁返回 409，不要排队。** 用现成的 `ErrorCode.TASK_ALREADY_RUNNING`
（`common/error/ErrorCode.java` 里已定义，HTTP 409）。

选跳过而不是排队的理由：报价刷新是覆盖写，跳过一轮最多晚 1 分钟；
排队会在上游恢复时把请求一起打出去，反而触发限流。

演示时手动点刷新撞上定时任务，前端要显示「正在刷新中」而不是静默无反应 ——
演示时静默比报错更尴尬。

MVP 是单实例部署，`AtomicBoolean` 够用。将来多实例再换数据库行锁或 ShedLock。

## 8. 写库语义

**一次刷新写两张表，放在同一个事务里。**

| 表 | 主键 | 写入语义 |
|---|---|---|
| `price_quote` | `symbol` | 一个代码一行，覆盖写 |
| `price_point` | `(symbol, captured_at)` | 追加；同键重复写是覆盖，不报错 |

复合主键让任务重跑安全 —— 同一个 `(symbol, captured_at)` 写两次仍然是一行。

**`captured_at` 必须用 provider 返回的时间，不是 `Instant.now()`。**

这条不是风格问题。`newsMarker` 要对齐到 `price_point` 这条时间轴上，
用写入时间的话标记线会偏离价格真正变动的位置。V7 脚本的注释里写了同样的话，
`price_quote.as_of` 也是同一条规则。

Finnhub 的 `/quote` 返回 `t` 字段（Unix 秒），转成 `Instant` 用它。
provider 没给时间戳时才退回当前时间，并且记一条日志。

**其余几条约定（详见 `⑤实体使用说明.md`）：**

- 钱和股数一律 `BigDecimal`，不用 `double`
- 比较 `BigDecimal` 用 `compareTo`，不用 `equals` —— `0.10` 和 `0.1` 的 scale 不同
- 时间一律 `Instant` 存 UTC
- `previousClose` 可以为 null（上市不足两个交易日，EC-19），不要填 0 —— 0 会让下游算出 -100% 的涨跌幅

## 9. 测试要求

架构 §7.2 的分层。这个任务至少要有下面四组。

**WireMock（集成层）**

| 用例 | 验证 |
|---|---|
| 正常响应 | 字段映射正确，`t` 转成 `Instant` |
| 429 | 不重试，异常不外抛，记日志 |
| 超时 | 同上 |
| 空响应 / 未知代码 | 返回 `Optional.empty()`，不写库 |

**Testcontainers（真 MySQL，不用 H2）**

| 用例 | 验证 |
|---|---|
| 同一 `(symbol, captured_at)` 写两次 | `price_point` 仍是一行 |
| 同一 symbol 刷新两次 | `price_quote` 仍是一行，值是最新的 |
| 未知 symbol | 被外键拒绝 |

H2 在 `DECIMAL` 精度和唯一索引长度上和 MySQL 不一致，用 H2 测过的照样可能在真库上失败。

**交易时段判断（单测）**

三个用例：盘中、收盘后、周末。时间通过参数注入 —— 所以第 6 节要求别在方法里调 `now()`。

**执行锁（集成测试，EC-20）**

锁被持有时，手动触发返回 409 而不是排队。
