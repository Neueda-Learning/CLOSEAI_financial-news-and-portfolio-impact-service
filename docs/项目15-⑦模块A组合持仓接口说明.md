契约（`项目15-③`）写的是端点**应该**长什么样，本文档写它们**实际**长什么样，以及调用时会踩到的地方。两者不一致时，以本文档为准并提 issue —— 实现和契约有出入是实现的 bug，不是契约的。

## 1. 九个端点

| 方法 | 路径 | 需求 | 成功码 |
|---|---|---|---|
| POST | `/api/v1/portfolios` | A1 | 201 |
| GET | `/api/v1/portfolios` | A2 | 200 |
| GET | `/api/v1/portfolios/{id}` | A2 | 200 |
| GET | `/api/v1/portfolios/{id}/summary` | B2、B3 | 200 |
| DELETE | `/api/v1/portfolios/{id}` | A3 | 204 |

`GET /{id}` 和 `GET /{id}/summary` 返回**同一个结构**。契约把它们列成两条，实现上详情页需要的字段和汇总完全重合，拆两个形状只会让前端多写一个类型。

新增持仓返回 **200 而不是 201**：重复代码会合并到已有持仓（EC-09），那次调用没有创建任何东西。

启动后 Swagger 在 `http://localhost:8080/swagger-ui.html`，字段说明以那里为准，本文档不重复列。

## 2. 前端必须知道的四件事

### 2.1 金额是字符串，比率是数字

```json
{
  "marketValue": "12560.00",
  "unrealizedPnL": "-1440.00",
  "unrealizedPnLPct": -10.29,
  "weight": 0.556738
}
```

不是随手写的。`JacksonConfig` 全局把 `BigDecimal` 序列化成字符串，金额过 JS 的 `Number` 会丢精度（SC-002 要求金额精确）；百分比和权重只用于显示，数字更省事。

**用 `decimal.js` 或字符串运算处理金额，不要 `parseFloat` 之后相加。**

### 2.2 `weight` 是比率，不是百分比

`0.556738` 表示 **55.67%**，自己乘 100。所有 `weight` 加起来等于 1.0（SC-003 要求 ±0.01% 内，实测是精确的 1.000000）。

### 2.3 `null` 字段会整个消失

`application.yml` 里 `default-property-inclusion: non_null`，所以字段为 null 时**不出现在 JSON 里**，不是 `"field": null`。

JS 里 `obj.weight` 两种情况都是 `undefined`，所以不影响判断，但 TypeScript 类型要写成可选：

```typescript
interface HoldingRow {
  weight?: number;      // 不是 number | null
  currentPrice?: string;
}
```

### 2.4 分页从 1 开始

```
GET /api/v1/portfolios/1/holdings?page=1&size=20
```

`page` 从 1 开始（契约 1.4），`size` 上限 100，超了会被截到 100 而不是报错。响应里的 `page` 回显的也是 1 基。

**权重是全组合口径，不是页内口径。** 分页端点会先估值整个组合再切页，所以第 2 页只有一条持仓时它的 `weight` 仍是 0.556738，不是 1.0。页内口径的权重每页都加到 100%，没有意义。

## 3. 报价缺失和过期（EC-13）

现在**所有持仓的 `quoteAvailable` 都是 `false`**，因为 `price_quote` 表是空的 —— 模块 B 的刷新任务还没上线。这是 EC-13 的正常路径，不是 bug。B 上线后自动变 `true`。

三种情况要分开处理：

| 情况 | `quoteAvailable` | `currentPrice` | `marketValue` |
|---|---|---|---|
| 有报价且新鲜 | `true` | 有值 | 有值 |
| 有报价但过期（超 5 分钟） | `false` | **有值**（最后已知价） | 有值 |
| 从未抓到过报价 | `false` | 不存在 | **不存在** |

第三种情况 `marketValue` 缺失是故意的 —— **不用成本价兜底**。编出来的估值看起来像真的，比缺失更糟，而且会污染组合总市值。

前端遇到 `quoteAvailable: false` 且 `currentPrice` 存在时，建议显示价格并标注「非实时」；两者都缺时显示「—」。

### 过期判断

```yaml
app:
  valuation:
    quote-freshness-budget-seconds: 300
```

报价刷新是每分钟一次，预算给了五倍，漏几轮不会误报。响应里 `stale: true` 表示**任一**持仓的报价过期或缺失 —— 总数只能和它最旧的输入一样新。`asOf` 是最旧那条报价的采集时间。

**空组合例外**：`stale` 是 `false`。它的零总值不依赖任何报价，没有东西会过期，给一个完全正确的数字挂过期标记是噪音（EC-01）。

## 4. 给模块 E 的服务层接口

§5.3 的公式要四个输入，其中两个是模块 A 的：持仓权重 `w` 和持仓市值（`valueImpact` 要乘的那个）。**不要自己再算一遍** —— 两套实现最终会算出不一样的数，SC-002/SC-003 检查的正是这个。

```java
@Service
public class ImpactService {

    private final PortfolioService portfolios;   // com.fnpis.service

    public void assess(Long portfolioId, String symbol, ...) {
        PortfolioWeights weights = portfolios.weights(portfolioId, Instant.now());

        PositionWeight position = weights.of(symbol).orElse(null);
        if (position == null || !position.assessable()) {
            return;   // 没持有，或有报价才能算 —— 见 4.2
        }

        BigDecimal w = position.weight();              // 0.302842，6 位精度
        BigDecimal value = position.marketValue();     // 38900.25
        // expectedImpact = s × c × w
        // valueImpact    = value × r
    }
}
```

### 4.1 权重在这条路径上是 BigDecimal

对外 API 返回的 `weight` 是 JSON 数字，但**服务层给的是 `BigDecimal`，6 位精度**。

因为你要把它乘进钱里（`s × c × w`、`w × r`），架构 6.2 要求金额全程不碰 `double`。而 `impact_assessment.holding_weight` 列就是 `DECIMAL(10,6)`，精度完全对齐，直接存不用转。

**别去调 HTTP 接口拿那个 Double 再转回来**，那会把这层设计要避免的舍入捡回去。

### 4.2 没报价的持仓会在 map 里，但值是 null

和饼图用的 `allocations()` 不一样 —— 那个会丢掉无报价的持仓（画不出未知大小的扇形），这条路径保留。因为你必须区分三种情况：

| 情况 | `of(symbol)` | `assessable()` |
|---|---|---|
| 持有且有报价 | 有值 | `true` |
| 持有但无报价 | 有值，`weight`/`marketValue` 为 null | `false` |
| 根本没持有 | `Optional.empty()` | — |

`holding_weight` 是 `NOT NULL` 列，所以 **`assessable() == false` 的要跳过，不要落库**。给 0 更糟 —— 读起来像「无影响」而不是「算不出」。

判断整个组合能不能评估用 `weights.isAssessable()`。

### 4.3 包可见性

`PortfolioService.weights()` 是 public，`PortfolioWeights` 和 `PositionWeight` 也是 public，但它们内部用的 `Valuation` 是包级私有。

你的类放 `com.fnpis.service` 包里没问题。**要放别的包，先告诉我，我把可见性调一下** —— 别自己改，那会绕过我刻意收窄的边界。

### 4.4 没有对应的 HTTP 端点

故意没加。走 HTTP 会多一层序列化，`BigDecimal` 变字符串又要 parse 回来，精度白设计。

如果前端最后要单独看权重，那时候再加端点，形状你定。

## 5. 校验规则与错误

请求体不合法时返回 400，格式是契约 6.1 的 problem+json，`errors` 数组逐字段列出：

```json
{
  "type": "https://api.fnpis.local/errors/validation-failed",
  "title": "Validation failed",
  "status": 400,
  "detail": "Request has 1 invalid field(s)",
  "code": "VALIDATION_FAILED",
  "errors": [
    { "field": "quantity", "message": "MVP 只接受整数股", "rejectedValue": "0.5" }
  ]
}
```

| 输入 | 结果 | 边界 |
|---|---|---|
| 组合名为空或超 100 字符 | 400 | EC-10 |
| 股票代码不在 `security` 表 | 404 `SECURITY_NOT_FOUND` | EC-05 |
| 数量为 0 或负数 | 400「数量必须为正数」 | EC-06 |
| 数量为小数（0.5 股） | 400「MVP 只接受整数股」 | EC-08 |
| 成本价为 0 | **通过**，盈亏百分比返回 null | EC-07 |
| 成本价为负数 | 400 | — |
| PATCH 空对象 `{}` | 400「至少要修改一个字段」 | — |
| `baseCurrency` 非 USD | 400「MVP 只支持 USD」 | AS-02 |
| 请求体不是合法 JSON | 400「请求体不是合法的 JSON」 | — |

代码大小写不敏感，`nvda` 会被规范化成 `NVDA` 存储。

### 成本价为 0 的处理（EC-07）

允许（可能是赠股），但 `unrealizedPnLPct` 返回 **null**，不是 0，也不是 `Infinity`/`NaN`。前端显示「—」。

同理 EC-22：组合总市值为 0 时 `weight` 返回 null，不做除零运算。

### 重复添加同一代码（EC-09）

不报错，**合并成一笔并重算加权均价**：

```
新成本价 = (原数量 × 原成本 + 新数量 × 新成本) ÷ (原数量 + 新数量)
```

例：先加 20 股 @ $100，再加 80 股 @ $150 → 100 股 @ **$140.00**。

不是两个价格取平均（那会算出 $125），仓位大小不同时结果差很远。

## 6. 本地怎么跑

```bash
cd backend
MYSQL_USER=root MYSQL_PASSWORD=root \
FINNHUB_KEY_NEWS=x FINNHUB_KEY_PRICE=x LLM_API_KEY=x \
./mvnw spring-boot:run
```

模块 A 不需要真的 API key，占位符就行 —— 它不调外部服务。

`security` 表由 V5 迁移脚本预置，直接可用。想看到非零市值就手动插报价：

```sql
INSERT INTO price_quote (symbol, price, previous_close, as_of)
VALUES ('NVDA', 125.60, 121.40, UTC_TIMESTAMP(3))
ON DUPLICATE KEY UPDATE price = VALUES(price), as_of = VALUES(as_of);
```

`as_of` 超过 5 分钟就会被判过期，测过期路径时把它往前调：

```sql
UPDATE price_quote SET as_of = DATE_SUB(UTC_TIMESTAMP(3), INTERVAL 10 MINUTE);
```

### 标的搜索为什么没做

契约 §759 自己写着「搜索行为（前缀匹配还是模糊匹配）未定」。前缀匹配能用索引，模糊匹配是 `LIKE '%x%'` 全表扫，猜错要重写。

它是新增持仓时的下拉搜索，属于前端体验优化 —— A4 本身不依赖它，直接 POST 一个代码，不存在就返回 404（EC-05 已实现）。

## 8. 已验证到什么程度

32 个单元测试，全部通过。九个端点在 MySQL 8.0.46 上逐个实跑过，不是只编译通过。

手算核对过的数字：

| 检查 | 手算 | 实际 |
|---|---|---|
| EC-09 加权均价 | (20×100 + 80×150)/100 = 140 | `140.00` |
| SC-002 总市值 | 50×200 + 100×125.60 = 22560 | `22560.00` |
| SC-002 总盈亏 | 22560 − 23000 = −440 | `-440.00` |
| SC-003 权重加总 | — | 精确 `1.000000` |
| §5.3 例 1 权重 | 38900.25 / 128450.75 | `0.302842`（文档的 0.303 是三位舍入） |

金额按行舍入到分，总数由这些行加出 —— 不是先加到四位精度再舍入。SC-002 是拿计算器加屏幕上的行跟总数对，会计意义上正确但和可见行差一分的总数过不了这个检查。

### 两个没验证的

**Checkstyle 本机跑不了**，插件包离线拉不到。手工核对了全部规则（行长、tab、`import *`、`System.out`、`double` 命名金额），但 **CI 上的结果才准**。

**EC-21**（估值过程中删除持仓）逻辑上成立 —— 估值方法是 `@Transactional(readOnly = true)`，InnoDB 默认 REPEATABLE READ，事务内读一致快照，不会崩。但这需要并发测试才能真正证明，**没有实测**。
