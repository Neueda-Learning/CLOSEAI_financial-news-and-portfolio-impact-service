# 1. 系统全貌

## 1.1 三条数据流

需求文档第 1 章说的那件事，用架构语言表达就是三条数据流的交汇：

| 数据流 | 来源 | 角色 | 谁负责 |
|---|---|---|---|
| 组合持仓 | 自有数据库 | 系统核心实体 | PortfolioService |
| 财经新闻 | 外部 API | 事件输入 | NewsService |
| 行情价格 | 外部 API | 结果验证 | MarketDataService |

三者由**情感分析 + 影响评估引擎**串联。
这个串联点是本项目唯一的原创逻辑，也是架构上最需要保护的部分。

## 1.2 数据怎么流动的

对应需求文档第 3 章那六步，在架构里是这样跑的：

```
用户建持仓
    │
    ▼
[数据库] 持仓表 ──────────────┐
                              │
定时任务每 15 分钟             │ 读 watchlist
    │                         │
    ▼                         ▼
[新闻 API] ──► 去重入库 ──► 新闻表
                              │
                              ▼
                        [情感分析引擎]
                              │
                              ▼
                          情感结果表
                              │
定时任务每天收盘后             │
    │                         │
    ▼                         ▼
[行情 API] ──► 日线表 ──► [影响评估引擎] ◄── 持仓权重
                              │
                              ▼
                          影响评估表
                              │
                              ▼
                      REST API ──► 前端联动视图
```

**关键点：前端从不直接触发外部 API 调用，所有外部数据都是定时任务预先落库的。**
这一点决定了整个架构的形状，理由见决策 2，
它同时是需求文档 SC-009（外部数据源不可用时页面仍可读）的实现基础。

## 每层的职责边界

| 层 | 能做什么 | 绝对不能做什么 |
|---|---|---|
| API 层 | 参数校验、DTO 转换、鉴权 | 写业务逻辑 |
| 应用服务层 | 全部业务规则、事务 | 直接调用第三方 HTTP |
| 集成层 | 调第三方、缓存、重试、格式转换 | 写业务规则 |
| 调度层 | 触发任务 | 实现业务逻辑（调服务层） |
| 持久层 | 存取数据 | 计算 |

> **最容易破坏的一条是"应用服务层不许直连第三方"。**
> 一旦有人为了赶进度在 Service 里直接发了个 HTTP 请求，
> 决策 1 和决策 2 的全部好处就一起丢了。Code Review 重点盯这个。

# 3. 关键架构决策

每条都是"问题 → 决策 → 理由 → 代价"，逐条评审。

## 决策 1：三个 Provider 接口，业务层只依赖接口

**问题**
免费 API 有四个不确定性：额度可能不够、服务可能挂、演示当天可能限流、
测试时不能真的去调外部接口。

**决策**
定义三个接口，业务层只依赖接口，第三方的响应结构在集成层就转成自己的领域对象。

```java
public interface NewsProvider {
    List<NewsArticle> fetchCompanyNews(String symbol, LocalDate from, LocalDate to);
}
public interface PriceProvider {
    Optional<PriceQuote> fetchQuote(String symbol);
    List<PriceBar> fetchDailyBars(String symbol, LocalDate from, LocalDate to);
}
public interface SentimentEngine {
    SentimentResult analyze(String headline);
    String modelVersion();    // 存入 sentiment_score.model_version
}
```

实现类与 Spring 装配：

| 接口 | 生产实现 | 测试实现 | 装配方式 |
|---|---|---|---|
| NewsProvider | `FinnhubNewsProvider` | `MockNewsProvider` | `@Profile` 或 `@ConditionalOnProperty` |
| PriceProvider | `FinnhubPriceProvider` | `MockPriceProvider` | 同上 |
| SentimentEngine | `AgentSentimentEngine` | `StubSentimentEngine` | 同上 |

用 `application.yml` 的 profile 切换，演示时改一个配置项就能全切 Mock：

```yaml
app:
  providers:
    news: finnhub      # finnhub | mock
    price: finnhub     # finnhub | mock
    sentiment: agent   # agent | stub

  sentiment:
    model: <模型名>          # 改动时同步 model_version
    temperature: 0
    prompt-version: v1
    max-concurrency: 3       # 控制批量分析时的并发
```

**理由**
这是整个架构里回报最高的一条决策，一次解决四件事：

| 好处 | 说明 |
|---|---|
| 换数据源不伤业务 | 第一天调研若发现 Finnhub 行情不够用，换一家只改 `integration/` 下的实现类 |
| E2E 测试可确定化 | 用 Mock Provider，测试结果每次一样，不依赖网络 |
| 演示日有后路 | 额度耗尽时切 Mock，演示照常进行 |
| 宕机降级演示 | 加一个开关让 Provider 假装挂掉，就能现场演示降级 |

**代价**
多写一层接口和转换代码，前期慢半天。**值得。**

---

## 决策 2：缓存优先读路径，过期状态对外可见

**问题**
免费 API 有频率限制。如果前端每次刷新都触发外部调用，几分钟就会被限流。

**决策**

- 所有外部数据先由定时任务落库，读接口**只读数据库**
- 响应体统一带两个字段：`asOf`（数据时间）和 `stale`（是否过期）
- 前端把这两个字段显示出来

**理由**
除了防限流，还有一个额外好处：**限流从缺陷变成了产品特性。**

演示时你可以主动说："这个数据是 12 秒前的缓存，上游此刻已经限流了，
系统照常工作，并且如实告诉用户数据的新鲜度。"
这比藏着掖着强得多，也直接呼应了需求文档的 B4。

**代价**
数据不是真正实时的。需求文档 §13.1 的问题 1 就是为了跟讲师确认这个口径。

---

## 决策 3：影响评估结果落库，不在读请求里现算

**问题**
影响评估依赖"某个特定时点的价格"。如果每次请求都现算，
同一条新闻在不同时刻查会得到不同结果，演示时无法复现，而且慢。

**决策**
定时任务算完写入 `impact_assessment` 表，读接口纯查询。

**理由**

- 结果可复现，演示前可以预热好数据
- 有审计轨迹，能回答"这个结论是什么时候、基于什么数据算出来的"
- 读接口快，不受计算耗时影响

**代价**
数据有延迟，需要一个"手动重算"接口给演示用。

---

## 决策 4：新闻按股票代码精确拉取，不做全局 feed 模糊匹配

**问题**
新闻怎么关联到持仓？如果拉全市场新闻再用文本匹配公司名，
准确率会很低（同名公司、别名、缩写），而演示效果直接取决于这个准确率。

**决策**
按 watchlist 里的每个代码分别调用"公司新闻"接口，返回的新闻天然属于该代码。
`match_method` 字段记录关联方式，为将来加模糊匹配留位置。

**理由**
关联准确率 100%，零文本处理成本。
MVP 阶段把 watchlist 固定在 **10~20 只大盘美股**，
**匹配准确率优先于覆盖范围** —— 前者直接决定演示效果，后者不影响。

**代价**
持仓多了调用次数线性增长，靠 watchlist 上限和缓存控制。

## 决策 5：情感分析用 LLM Agent，单一实现

**问题**
PDF 允许三种情感分析做法（词典 / 本地模型 / AI API）。
团队决定**只做 Agent 方案**，不做多引擎对比。

**决策**
调用 LLM API 分析新闻标题，返回结构化情感结果。**不实现词典版和本地模型。**

```java
public interface SentimentEngine {
    SentimentResult analyze(String headline);
    String modelVersion();    // 存入 sentiment_score.model_version
}
```

| 实现 | 用途 |
|---|---|
| `AgentSentimentEngine` | 生产实现，调 LLM API |
| `StubSentimentEngine` | **测试专用**，返回固定结果 |

**接口保留，但目的变了。**
不再是为了"多引擎切换"，而是为了**测试和演示能脱离外部 LLM 服务** ——
理由和决策 1 的 Provider 接口完全一样，见下面的代价一节。

**输出契约**（需求文档 §5.2 约定，这里定实现）

要求 LLM 返回严格 JSON，不要自然语言：

```json
{ "label": "POSITIVE", "score": 0.72, "confidence": 0.88 }
```

后端**必须校验**再落库，不能信任 LLM 输出：

| 校验项 | 不合规时 |
|---|---|
| `label` ∈ {POSITIVE, NEGATIVE, NEUTRAL} | 整条丢弃，标记分析失败 |
| `score` ∈ [-1, 1] | 同上 |
| `confidence` ∈ [0, 1] | 同上 |
| score 与 label 方向自洽 | 以 score 为准重算 label |

配置：`temperature = 0`，同一标题尽量得到同样结果。
prompt 和模型名写进配置文件，改动时同步 `model_version`。

**理由**
准确率明显高于词典版，而且省掉了维护正负词表的工作量。
财经标题里"beats estimates""raises guidance"这类表达，词典版靠词频命中很难判准，
LLM 直接就能理解。

**代价（三条，都要处理）**

**1. 结果不完全可复现。** 这是与需求文档 §5.2"可复现"约束的**真实冲突**。
即使 `temperature = 0`，LLM 也不保证逐字一致，且模型会在服务端更新。
对策：情感结果**一次算完就落库**，之后所有读取都用库里那条，不重新调用。
演示复现的是**库里的结果**，不是重新分析的结果。

**2. 每条新闻都要花钱和时间。** 词典版是本地纯计算，Agent 每条都是一次网络请求。
对策：只分析未分析过的新闻（靠 `sentiment_score` 是否已有记录判断），
绝不重复分析；批量处理时控制并发。

**3. 测试和 CI 不能依赖真实 LLM。** 这就是接口必须保留的原因 ——
`StubSentimentEngine` 让单元测试、集成测试、E2E 全部确定化，CI 里不需要 LLM key。

**4. 标题是外部不可信输入，存在 prompt 注入风险。**
新闻标题来自 Finnhub，理论上可能包含"忽略前面的指令"这类文本。
对策：prompt 里把标题放在明确的数据边界内，并且**只接受符合上面 schema 的输出**，
校验不通过就丢弃。这条不是洁癖，是标题内容本来就不受我们控制。

## 决策 6：日线表是影响计算的唯一价格来源

**问题**
影响计算需要"当日收盘 vs 前一日收盘"。如果每次都去查外部历史接口，
额度很快耗尽，而且历史数据本来就是不变的，反复查毫无意义。

**决策**
每天收盘后由定时任务写一次 `price_bar` 表，影响引擎只读这张表，不碰外部 API。

**理由**
历史数据只拉一次，额度花在实时报价上。附带把组合价值走势图的数据源也解决了。

**代价**
`price_bar` 是数据量最大的表，需要在 `(symbol, trade_date)` 上建索引。

## 复杂度汇总（这些多出来的东西都不是过度设计）

六条决策各自都多引入了一点复杂度。汇总在一起看，每一条都能回答
"为什么不用更简单的方案"——评审时按这张表逐行过一遍即可。

| 引入的复杂度 | 对应决策 | 更简单的方案是什么 | 为什么那个方案不够 |
|---|---|---|---|
| Provider 接口层 | 决策 1 | 业务代码直接发 HTTP 请求 | 换源、测试确定化、演示留后路、宕机降级演示，四个场景全部需要 |
| 缓存优先读路径 | 决策 2 | 每次请求都实时查外部 API | 免费额度几分钟内就会被限流 |
| 影响结果落库 | 决策 3 | 每次请求现算 | 不可复现，演示当天结果可能对不上 |
| 独立关联表 | 决策 4 / §4.3 要点2 | news_article 表里放一个 symbol 字段 | 一条新闻可影响多只股票，单字段存不下多对多关系 |
| SentimentEngine 接口 | 决策 5 | 直接在 Service 里调 LLM | 测试和 CI 不能依赖真实 LLM，需要 Stub 实现 |
| 日线表落库 | 决策 6 | 每次现查历史行情接口 | 历史数据本身不变，重复查询纯粹浪费额度 |

如果评审时有人对某一行有异议，说明简单方案在当前约束下其实够用——
回去改决策，不要绕开这张表硬争论。

## 4.2 表清单与最小字段

需求文档 §10.1 已列出业务视角的字段，这里补充技术约束。

| 表 | 主键 | 关键索引 / 约束 |
|---|---|---|
| portfolio | id | — |
| holding | id | FK portfolio_id，索引 (portfolio_id, symbol) |
| security | symbol | — |
| news_article | id | **UNIQUE (external_id)** ← 去重靠这个 |
| article_security_link | (article_id, symbol) | 复合主键，天然防重 |
| sentiment_score | id | **UNIQUE (article_id)** ← 单引擎，一篇一条 |
| price_quote | symbol | 每个代码只保留最新一条 |
| price_bar | (symbol, trade_date) | 复合主键 |
| price_point | (symbol, captured_at) | 复合主键，主键顺序即查询顺序，无需额外索引 |
| impact_assessment | id | **UNIQUE (article_id, symbol, portfolio_id, attribution_date)**，索引 (portfolio_id, attribution_date) |
| portfolio_valuation_snapshot | (portfolio_id, snapshot_date) | 复合主键 |

`holding` 上的 (portfolio_id, symbol) 是**唯一约束**而非普通索引：EC-09 要求重复添加
合并成一笔，有唯一约束时 Service 层写错会变成插入失败，而不是静默拆成两行。

`impact_assessment` 的唯一约束必须带 `symbol` —— EC-24 规定一条新闻影响多个持仓时
各占一行。有这个约束，`/impacts/recompute` 就是幂等 upsert；没有的话只能先 DELETE
再 INSERT，中途失败会在当日数据里留个洞。

**`price_point` 是三张最初漏掉的表之一**，但它最急：日内价格点采集不回来，
免费数据源不提供历史分钟线。`price_bar` 缺了还有 §6.3 的报价兜底，这张没有。
报价刷新任务必须从「更新 price_quote」改成「更新 price_quote **并追加** price_point」。

## 4.3 三个建模要点

**要点 1：`news_article.external_id` 必须建唯一索引**
去重完全依赖它。没有这个约束，定时任务重复跑就会插入重复新闻。

**要点 2：新闻与股票必须用独立关联表**
一条新闻可以影响多只股票（"芯片股集体大涨"），一只股票有多条新闻。
这是多对多。**在 news_article 表里放一个 symbol 字段是最容易犯的建模错误**，
一旦这么做了，后面要改就得动迁移脚本和所有相关查询。

**要点 3：`sentiment_score.article_id` 建唯一索引**

只做 Agent 单引擎（决策 5），一条新闻只有一份情感结果，
所以 `article_id` 可以且应该建 `UNIQUE`：

```sql
CREATE TABLE sentiment_score (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  article_id    BIGINT       NOT NULL,
  label         VARCHAR(16)  NOT NULL,   -- POSITIVE / NEGATIVE / NEUTRAL
  score         DECIMAL(5,4) NOT NULL,   -- -1 ~ 1
  confidence    DECIMAL(5,4) NOT NULL,   -- 0 ~ 1
  model_version VARCHAR(64)  NOT NULL,   -- 模型名 + prompt 版本
  analyzed_at   DATETIME(3)  NOT NULL,
  CONSTRAINT fk_sentiment_article FOREIGN KEY (article_id)
      REFERENCES news_article(id) ON DELETE CASCADE,
  UNIQUE KEY uq_sentiment_article (article_id)
);
```

这个唯一约束顺带解决了一个实际问题：**它保证同一条新闻不会被重复分析**。
情感分析任务用 `INSERT ... ON DUPLICATE KEY UPDATE` 或先查再插，
即使任务重跑也不会产生重复的 LLM 调用（省钱，对应决策 5 的代价 2）。

> **`model_version` 字段保留。** 虽然不做多引擎对比了，但换模型或改 prompt 后
> 要能分辨"这条结论是哪个版本算的"。字段很便宜，出问题时它是唯一线索。

> **仓库 README 的表设计在这一点上是对的**（`news_id UNIQUE`），
> 此前架构文档写的是"不能唯一"，那是基于多引擎方案。**现在以本节为准。**

## 4.4 MySQL 字段类型约定

**全库统一 `utf8mb4` / `utf8mb4_0900_ai_ci`。**
新闻标题里有 emoji 和特殊符号，用 `utf8` 会插入失败。

| 用途 | MySQL 类型 | Java 类型 | 说明 |
|---|---|---|---|
| 主键 id | `BIGINT AUTO_INCREMENT` | `Long` | — |
| 股票代码 | `VARCHAR(16)` | `String` | 美股代码最长 5 位，留余量 |
| 金额、价格 | `DECIMAL(18,4)` | `BigDecimal` | **禁止 DOUBLE**，见 §6.2 |
| 数量（股数） | `DECIMAL(18,4)` | `BigDecimal` | MVP 只收整数，但留碎股余地 |
| 比率、权重 | `DECIMAL(10,6)` | `BigDecimal` | 权重、涨跌幅、情感分值 |
| 情感分值 score | `DECIMAL(5,4)` | `BigDecimal` | 范围 -1 ~ 1 |
| 时间戳 | `DATETIME(3)` | `Instant` | **存 UTC**，毫秒精度 |
| 交易日 | `DATE` | `LocalDate` | 归因日、日线日期 |
| 枚举 | `VARCHAR(24)` | Java enum | `@Enumerated(EnumType.STRING)` |
| 新闻标题 | `VARCHAR(512)` | `String` | 超长截断，不用 TEXT |
| 原文链接 | `VARCHAR(1024)` | `String` | — |
| 外部唯一 id | `VARCHAR(128)` | `String` | 建 UNIQUE 索引，见要点 1 |

**两个 MySQL 特有的坑：**

1. **`VARCHAR` 上建 UNIQUE 索引有长度限制。** utf8mb4 下单列索引上限约 191 字符
  （旧版本 767 字节限制）。`external_id` 定 `VARCHAR(128)` 是安全的，不要放大到 512。
2. **`DATETIME` 不带时区，`TIMESTAMP` 会自动转时区。** 我们统一用 `DATETIME(3)` 存 UTC，
  由应用层负责时区转换，避免数据库时区配置影响数据。

## 4.5 建表脚本组织

Flyway 脚本放 `backend/src/main/resources/db/migration/`：

```
V1__create_core_tables.sql          security, portfolio, holding
V2__create_news_tables.sql          news_article, article_security_link, sentiment_score
V3__create_price_tables.sql         price_quote, price_bar
V4__create_impact_table.sql         impact_assessment
V5__seed_watchlist.sql              初始 10~20 只标的（实际 15 只）
V6__create_valuation_snapshot.sql   portfolio_valuation_snapshot
V7__create_price_point_table.sql    price_point
```

V6 和 V7 是落地时补的两张表 —— §4.2 原表清单没有它们，但 §5 的收盘快照任务和契约的
`impact-view` 分别依赖它们，没有别的数据源。详见 `项目15-④数据库说明.md`。

**已提交的脚本不许改，只能加新版本。** 改了会导致 Flyway 校验和不匹配，
其他人拉代码后启动失败。

# 5. 定时任务

| 任务 | 频率 | 做什么 | 依赖 |
|---|---|---|---|
| 新闻轮询 | 15 分钟 | 遍历 watchlist 增量拉新闻，按 external_id 去重 | NewsProvider |
| 情感分析 | 新闻入库后触发 | 只处理 `sentiment_score` 里没有记录的新闻 | SentimentEngine（LLM） |
| 报价刷新 | 1 分钟（仅交易时段） | 更新 price_quote **并追加一行 price_point** | PriceProvider |
| 收盘快照 | 每日收盘后 | 写 price_bar + portfolio_valuation_snapshot | PriceProvider |
| 影响重算 | 收盘快照完成后 | 生成当日 impact_assessment | 以上全部 |

> **报价刷新那条的「追加 price_point」不是可选项。** 联动视图的曲线只能从这张表来，
> 而日内点采集不回来 —— 任务没写，那一天的曲线就永久缺失。这是演示脚本第 4 步的核心画面。

## 依赖顺序

```
新闻轮询 ──► 情感分析 ──┐
                        ├──► 影响重算
收盘快照 ───────────────┘
```

影响重算必须在情感分析和收盘快照都完成后执行，否则数据不全。

> **收盘快照这个任务别省。**
> 没有它就画不出组合价值走势图（需求 F5），
> 而免费额度不够反复回查历史数据。

## 并发控制

免费 API 慢的时候，任务重叠是必然会发生的，必须显式处理。

**规则：每个任务持有一把以任务名为键的执行锁。拿不到锁就跳过本轮，记一条日志，不排队。**

要覆盖两个不同的场景：

| 场景 | 说明 | 对应需求 |
|---|---|---|
| 任务自身重叠 | 15 分钟到点了，但上一轮因为 API 慢还没跑完 | EC-23 |
| 手动与定时相撞 | 演示时点了手动刷新，刚好撞上定时触发 | EC-20 |

**选择"跳过"而不是"排队"的理由**：新闻轮询是幂等的（靠 external_id 去重），
跳过一轮最多晚 15 分钟拿到新闻，而排队会在 API 恢复时造成请求堆积，
反而更容易触发限流。

**Spring 下的具体实现：**

`@Scheduled` 默认单线程串行执行，同一个任务方法**天然不会重叠** ——
EC-23（任务自身重叠）用 `fixedDelay` 而非 `fixedRate` 就已经解决：

```java
// fixedDelay：上一轮结束后再等 15 分钟，永不重叠
@Scheduled(fixedDelayString = "${app.schedule.news-poll-delay:900000}")
public void pollNews() { ... }
```

但 EC-20（手动触发撞定时触发）仍需显式锁，因为手动触发走的是 HTTP 线程：

```java
private final AtomicBoolean running = new AtomicBoolean(false);

public boolean tryRun() {
    if (!running.compareAndSet(false, true)) {
        return false;            // 拿不到锁，调用方给出"正在刷新中"
    }
    try { doPoll(); } finally { running.set(false); }
    return true;
}
```

**注意**：如果给 `@Scheduled` 配了线程池（`spring.task.scheduling.pool.size > 1`），
不同任务会并行，此时 `fixedDelay` 只保证同一任务不重叠，跨任务的依赖顺序仍要靠上面的依赖图控制。

MVP 单实例部署，`AtomicBoolean` 足够。若将来跑多实例，改用数据库行锁或 ShedLock。

## 演示相关的手动触发

需求文档 C6 要求有手动刷新按钮。建议每个定时任务都提供一个手动触发接口，
演示时不用等 15 分钟。

手动触发同样要过上面那把锁。演示时如果拿不到锁，
界面要明确提示"正在刷新中"，不能静默无反应 —— 演示时静默无反应比报错更尴尬。

## 6.2 几个需要统一的实现约定

这几条不统一，多人协作一定会出问题。

**金额与数量一律用 `BigDecimal`，禁止 `double`/`float`。**
钱用浮点数算会出现 `0.1 + 0.2 = 0.30000000000000004`，
演示时讲师手工验算对不上，直接砸掉 SC-002。
MySQL 侧对应 `DECIMAL`，见 §4.4。

**JSON 输出时金额序列化为字符串。**
JavaScript 的 Number 是双精度浮点，大额金额传过去会丢精度。
Jackson 配 `WRITE_BIGDECIMAL_AS_PLAIN` 并按字符串输出，
前端只负责展示，不做金额运算。

**时间全部用 UTC 存储，`Instant` 类型，展示层再转时区。**
Finnhub 返回 Unix 时间戳，美股交易时段在美东时区，
用户在中国时区看页面 —— 三个时区混在一起不统一就会算错归因日（EC-16/EC-17）。
JDBC 连接串显式设置 `connectionTimeZone=UTC`。

**枚举在数据库里存字符串，不存序号。**
`POSITIVE`/`CONFIRMED` 这类值存 `VARCHAR`，用 `@Enumerated(EnumType.STRING)`。
存序号的话以后往枚举中间插一个值，历史数据全错。

## 6.3 数据源风险与对策（重要）

团队决定新闻用 Finnhub，行情用 Finnhub（主）+ Twelve Data（备用）+ yfinance（离线批量下载）。

**风险 1：服务商单点依赖——已缓解。** Twelve Data 作为行情备用已经在 `PriceProvider` 接口里
有了第二个实现。Finnhub 新闻宕机时新闻链路暂时降级到缓存（`news_article` 表），
行情链路切到 Twelve Data，两条链路各有独立 fallback。

**风险 2：PDF 的"多个外部 API 集成"怎么讲。**
现在有三家：Finnhub（新闻 + 行情主力）、Twelve Data（行情备用）、yfinance（离线数据准备）。
"集成多个外部数据接口"这一点已有冗余。

**风险 3（可能阻塞影响引擎，最高优先级）：免费版的历史日线接口是否可用。**

> 注意：**这一条多个账号解决不了。** 如果免费版根本不提供某个端点，
> 换几个 key 都是同样的结果 —— 额度问题和权限问题是两件事。

决策 6 要求影响引擎从 `price_bar` 表读"当日收盘 vs 前一日收盘"。
如果 Finnhub 免费版不提供历史日线（`/stock/candle` 一类端点），
E4 和 SC-007 会直接失去数据来源。**第一天必须先测这一条。**

免费版政策会变动，本文档不对当前配额下断言。三种可能结果：

| 场景 | 应对 |
|---|---|
| Finnhub 日线可用 | Finnhub 主力行情，Twelve Data 备用 |
| Finnhub 日线不可用 | Twelve Data 扛历史日线（800 req/day），Finnhub 仍负责报价和新闻 |
| 两家都不可用 | yfinance 批量下载 CSV 导入 `price_bar` 播种 |

> Twelve Data 免费版 800 req/day，5 只标的足够轮询。yfinance 无频率限制，用于播种期批量下载 CSV 导入 `price_bar`。

> **播种数据有时间成本**：要提前几天开始跑收盘快照，
> 才能在演示当天有足够数据画走势图并满足 SC-008 的 20 条样本。
> 所以这条调研越早做越好，不要拖到最后一周。

**前端框架由前端同学自行决定**（React / Vue / 其他均可）。

## 6.5 多 key 设计：按用途隔离额度

团队决定用多个 Finnhub 账号，新闻和行情各用独立的 key，不共用一个。

**架构上要做的事只有一件：让 key 的选择成为集成层的内部细节。**

```yaml
finnhub:
  base-url: https://finnhub.io/api/v1
  keys:
    news:  ${FINNHUB_KEY_NEWS}      # 新闻轮询专用
    price: ${FINNHUB_KEY_PRICE}     # 报价与日线专用
```

`FinnhubNewsProvider` 只读 `news` 那个 key，`FinnhubPriceProvider` 只读 `price` 那个，
业务层完全不知道有几个 key 存在。

**四条实现要求：**

1. **限流器按 key 分别配置，不要共用一个 Resilience4j 实例。**
  共用的话新闻轮询把限流器打满，报价刷新会跟着被拒 —— 那多个 key 就白配了。
  每个 key 一个独立的 `RateLimiter` 实例。

2. **429 响应只降级对应那条链路。** 新闻 key 被限流时，行情照常工作，
  页面上只有新闻区显示过期标记。这正好强化了决策 2 的降级演示效果。

3. **key 绝不能进日志。** 记请求 URL 时把 `token` 参数脱敏成 `token=***`。
  多个 key 意味着泄漏面变大，这条更要紧。

4. **`.env.example` 里列出全部 key 变量名，值留空。**
  新成员一眼知道需要准备几个账号，对应 SC-011。

**两件必须实测的事：**

| 要测什么 | 为什么 |
|---|---|
| 限流是按 key 还是按 IP | **如果按 IP，多个账号在同一台机器上不起作用**，这个方案的前提就不成立 |
| 免费版条款是否允许一人多账号 | 多账号绕额度在多数服务商的条款里是明确禁止的，最坏情况是账号被封 |

> **第一条是技术前提，第二条是团队自己的判断。**
> 我把它们写进文档不是要否决这个决定，而是因为**最坏的情况是演示前一天账号全被封**。
> 无论怎么选，`.env` 里都要留一套能立刻切 Mock 的配置（§8.1），
> 演示日的兜底方案不能只有"希望 key 还活着"。

## 7.2 测试策略

| 层次 | 工具 | 怎么测 | 重点 |
|---|---|---|---|
| 单元测试 | JUnit 5 + Mockito | Mock 掉 Provider | **影响评估引擎必须有单测**，用需求文档 §5.3 的三个算例 |
| 集成测试 | `@SpringBootTest` + **Testcontainers MySQL** | 真实 MySQL + Mock Provider | 定时任务、去重逻辑、Flyway 脚本 |
| 集成层测试 | **WireMock** | 桩掉 Finnhub 与 LLM 的 HTTP 响应 | 字段映射、限流重试、异常处理 |
| 情感输出校验 | JUnit 5 | 喂畸形 LLM 响应 | **必须测**：非法 label、score 越界、返回非 JSON、score 与 label 不自洽 |
| E2E 测试 | Playwright 或 Cypress | 全部 Mock Provider | 保证结果确定，不依赖网络 |

> **集成测试用 Testcontainers 起真实 MySQL，不要用 H2。**
> H2 的兼容模式和 MySQL 在 `DECIMAL` 精度、日期函数、唯一索引长度限制上都有差异，
> 用 H2 测过的 Flyway 脚本在真 MySQL 上照样可能失败 —— 那就白测了。

> 需求文档 §5.3 那三个算例（CONFIRMED / DIVERGENT / INCONCLUSIVE）
> 就是为了直接拿来当测试用例设计的，对应成功标准 SC-012。

**需求文档第 8 章的边界条件（EC-01 到 EC-24）建议逐条对应一个测试。**
那 24 条是照着真实 bug 场景列的，其中三条是除零陷阱，
必须有测试：EC-07（成本价为 0）、EC-18（缺前收盘价）、EC-22（总市值为 0 算权重）。

EC-20 和 EC-23 两条并发场景对应 §5 的执行锁设计，放集成测试。

```
frontend:  setup-node → npm ci → build → lint
```

## 7.4 Docker

`docker-compose.yml` 起三个服务：

| 服务 | 镜像 | 要点 |
|---|---|---|
| mysql | `mysql:8` | 配 `healthcheck`，挂 volume 持久化数据 |
| backend | 本地构建 | `depends_on: mysql: condition: service_healthy` |
| frontend | 本地构建 | 反代或直连后端 |

**MySQL 的健康检查不能省。** 后端启动时 Flyway 会立刻连库，
MySQL 容器启动比进程就绪慢好几秒，不等健康检查后端会启动失败。
后端侧也建议配连接重试。

后端 Dockerfile 用多阶段构建（Maven 构建层 + JRE 运行层），镜像小很多。

README 里的快速开始：克隆 → 复制 `.env.example` 为 `.env` 填 Finnhub key →
`docker compose up` → 访问前端地址。对应成功标准 SC-011。

## 7.5 密钥管理

**三个** key 都走环境变量：Finnhub 新闻、Finnhub 行情、**LLM API**。
`application.yml` 里用 `${FINNHUB_KEY_NEWS}` / `${FINNHUB_KEY_PRICE}` / `${LLM_API_KEY}` 占位，
**不写默认值**（写了默认值等于把 key 提交进仓库的风险敞口）。
`.env` 进 `.gitignore`，仓库里提交 `.env.example`（变量名齐全，值留空）。

**key 泄露到 GitHub 是真会发生的事故**，第一天就把 gitignore 配好。
多个 key 意味着泄漏面更大，两条额外要求：

- 日志里的 `token` 参数与 `Authorization` 头一律脱敏（§6.5 要求 3）
- CI 里用 GitHub Secrets，不要在 workflow 文件里写 key；
  **CI 完全不需要真 key** —— Finnhub 走 WireMock，情感走 `StubSentimentEngine`

> **LLM key 比 Finnhub key 更要紧**：Finnhub 免费 key 泄露最多是额度被用光，
> LLM key 泄露是**直接产生费用**。这个 key 单独确认一遍 gitignore 生效。

启动时校验 key 是否存在，缺失就快速失败并打印清楚缺哪个变量 ——
比运行几分钟后收到一堆 401 好排查。
