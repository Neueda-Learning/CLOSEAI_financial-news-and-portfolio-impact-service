## 1. 必须合入前修的（2 条）

### 1.1 `orElseGet(PriceQuote::new)` 丢了 `symbol`，写入必然失败

`service/QuotePersistenceService.java:35-36`

```java
PriceQuote q = quoteRepo.findById(symbol)
        .orElseGet(PriceQuote::new);     // ← symbol 没传，也没有后续 setSymbol
q.setPrice(s.price());
if (s.previousClose() != null) { ... }
q.setAsOf(...);
quoteRepo.save(q);
```

上一轮 §3.7 我提了两件事：一是 `orElse` 改 `orElseGet`（求值时机），
二是**建议构造器只传 `symbol`，其余交给 setter**。第二条只落实了一半 ——
构造器参数全删了，但漏了把 `symbol` 补回来。全分支 `grep setSymbol` 只有零个调用点。

后果是 **symbol 为空的新行**：

- `@Id` 为 null，`save()` 走 `persist()` 而不是 `merge()`
- `price_quote.symbol` 是 `VARCHAR(16) NOT NULL` 且 `PRIMARY KEY`，
  还带 `fk_quote_security FOREIGN KEY (symbol) REFERENCES security (symbol)`（V3:15-16）
- 插入抛异常，`@Transactional` 回滚，`price_point` 那行也一起没了

**首次刷新时 `price_quote` 是空表**（V3 建表，没有 seed），
所以 `findById` 对每个 symbol 都返回 empty，**每一个 symbol 都走这条空构造器分支**。
也就是说这不是边界情况，是主路径：模块 B 的写入从第一次运行起就 100% 失败，
`price_quote` 和 `price_point` 都是空表。

现在没暴露出来，只因为这条路径没有集成测试 —— `QuoteRefreshSchedulerTest` 测的是
`isTradingHours`，`persist` 完全没有覆盖。

**修法：** 两行任选其一。

```java
// A：构造器带 symbol（保留 4 参构造器，其余传 s 的值）
.orElseGet(() -> new PriceQuote(symbol, s.price(), s.previousClose(), s.capturedAt()))

// B：无参构造器 + 显式 setSymbol（配合上一轮 §3.7 的可读性建议，我更推荐这个）
PriceQuote q = quoteRepo.findById(symbol).orElseGet(PriceQuote::new);
q.setSymbol(symbol);      // ← 补这一行；已存在的行重复 set 同值无害
```

选 B 的话 `setSymbol` 放在 `orElseGet` 之后无条件执行，不用区分新旧行。
注意 `PriceQuote` 的 4 参构造器还在被 `PortfolioWeightsTest:119` 和
`ValuationServiceTest:182` 用着，**不要删它**。

**顺带请补一个 `QuotePersistenceServiceTest`。** 这个 bug 的特征是「只在空表首刷时触发」，
只有真正 save 一次才看得见。`@DataJpaTest` 或 Testcontainers 都行 ——
断言 `persist("AAPL", snapshot)` 之后 `quoteRepo.findById("AAPL")` 存在，
且 `getSymbol()` 等于 `"AAPL"`。同一个测试还能顺手钉住 `price_point` 那行的
`captured_at` 用的是 provider 时间而不是 `now()`。

### 1.2 `ClosingSnapshotService` 用服务器时区，且抓的是「今天」不是「上一个交易日」

`service/ClosingSnapshotService.java:51`

```java
LocalDate today = LocalDate.now();
List<DailyBar> bars = priceProvider.fetchDailyBars(symbol, today, today);
```

三个问题叠在一起：

**(a) 裸 `LocalDate.now()`。** 上一轮 §3.3 提过同一个坑，`NewsFetchService` 那边修了，
这个新写的类又踩回去。`ClosingSnapshotScheduler` 已经注入了 `Clock`
（`ClosingSnapshotScheduler:32`）却没往下传，service 自己拿系统默认时区。
容器（UTC）和笔记本（Asia/Shanghai）跑出来是两个日期。

**(b) 时区不是市场时区。** cron 是 `0 5 16 * * MON-FRI` + `zone = "America/New_York"`，
也就是 **ET 16:05** 触发。这个时刻在 UTC 是次日 20:05 或 21:05（夏令时 20:05），
在 Asia/Shanghai 是**次日 04:05**。于是：

| 部署时区 | ET 16:05 触发时 `LocalDate.now()` | 想要的日期 | 差 |
|---|---|---|---|
| America/New_York | 7-29 | 7-29 | ✅ |
| UTC | 7-29（20:05Z，同一天） | 7-29 | ✅ 侥幸 |
| Asia/Shanghai | 7-**30**（04:05 CST） | 7-29 | ❌ 差一天 |

Docker 容器默认 UTC 所以侥幸对，本地开发在国内跑就错一天。
Twelve Data 的 `time_series` 拿 7-30 这个未来日期，`values` 里没有这一天，
`filter` 全部滤掉 → `bars.isEmpty()` → 每个 symbol 都 `continue`，
日志报 `0/15 symbols captured`。**`price_bar` 静默保持空表**，
排查时会以为是 API key 或配额问题。

**(c) Javadoc 说的和代码做的不一致。** 方法 Javadoc 写着：

> Captures bars for yesterday (the last completed trading day).

代码传的是 `today`。ET 16:05 触发时「今天」的收盘刚出来，取 `today` 其实是对的意图，
但注释说 yesterday —— 下一个人按注释改成 `today.minusDays(1)` 就会拿到前一天的收盘，
而且**同样不报错**。两者必须对齐。

**修法：** 日期在 scheduler 算好传进来，或者 service 注入 `Clock` 并显式用市场时区：

```java
// ClosingSnapshotService
private static final ZoneId MARKET_ZONE = ZoneId.of("America/New_York");

public int capture() {
    LocalDate sessionDate = LocalDate.ofInstant(Instant.now(clock), MARKET_ZONE);
    ...
}
```

`QuoteRefreshScheduler` 已经有 `MARKET_ZONE` 这个常量了，三处
（两个 scheduler + 这个 service）用的是同一个市场时区，
建议提到一个共用常量上，别各写一份。

并把 Javadoc 改成实际语义：「Captures bars for the current ET session,
which has just closed when the 16:05 ET cron fires」。

**另外提醒一句关于归因日的口径：** D/E 侧 `AttributionDateResolver`
也是用 `America/New_York` 算归因日的。如果这里算出来的 `trade_date` 和
D/E 算出来的归因日差一天，E 会去 `price_bar` 找一个不存在的日期，
结果是 `INCONCLUSIVE` —— 而 §附 里说好的是「假日才 INCONCLUSIVE」。
时区不一致会让这个约定悄悄失效，这也是我把它列成必修的原因。

`ClosingSnapshotService` + `ClosingSnapshotScheduler` + `PriceBarRepository` 齐了，
`TwelveDataPriceProvider.fetchDailyBars` 是真实现（`/time_series`）。这解决了上一轮 §2 的排期问题，
**E 可以走 `price_bar` 主路径了** —— 谢谢，这对 SC-007 是关键。

但 `fetchDailyBars` 只有 Twelve Data 一家实现，其余三处仍然 `throw`：

| 位置 | 状态 |
|---|---|
| `integration/twelvedata/TwelveDataPriceProvider.java:57` | ✅ 真实现 |
| `integration/finnhub/FinnhubPriceProvider.java` | ❌ throw |
| `integration/WritePriceProvider.java:58` | ❌ **throw ← 这个是问题** |
| `integration/ChainedPriceProvider.java` | ❌ throw（读路径，暂时不影响） |
| `integration/db/DbPriceProvider.java` | ❌ throw |
| `integration/mock/MockPriceProvider.java` | ❌ throw |

`ClosingSnapshotService:33` 注入的是 `@Qualifier("writePriceProvider")`，
而 `WritePriceProvider.fetchDailyBars` 直接 `throw UnsupportedOperationException`。
`capture()` 的 try-catch 会吞掉它（`catch (Exception e)` → `log.warn` → 下一个 symbol），
所以**收盘快照跑完是 `0/15`，一行都不写，而且只在 warn 级日志里留痕**。

这条严格说不是「写错了」而是「链没接完」，但效果和 §1 的两条一样是 `price_bar` 空表。
我把它放在 §2 是因为修法是补功能不是改 bug：

```java
// WritePriceProvider
@Override
public List<DailyBar> fetchDailyBars(String symbol, LocalDate from, LocalDate to) {
    try {
        List<DailyBar> bars = finnhub.fetchDailyBars(symbol, from, to);
        if (!bars.isEmpty()) {
            return bars;
        }
    } catch (UnsupportedOperationException e) {
        // Finnhub free tier has no candle endpoint — fall through
    } catch (Exception e) {
        log.warn("Finnhub daily bars failed for {}, trying Twelve Data", symbol, e);
    }
    return twelvedata.fetchDailyBars(symbol, from, to);
}
```

Finnhub 免费档没有 candle 端点（这是上一轮 §6.3 那个「最高优先级」问题的答案），
所以其实可以更简单：`WritePriceProvider.fetchDailyBars` 直接 `return twelvedata.fetchDailyBars(...)`,
并在注释里写明「Finnhub free tier has no candle endpoint; Twelve Data only」。
少一层无意义的 try-catch，意图也更清楚。

**这条和 §1 的两条是同一件事的三个必要条件**：`symbol` 补上、日期算对、
`fetchDailyBars` 接通，缺任何一个 `price_bar` 都是空的。三条一起验证。

## 3. 中低优先级（4 条）

### 3.1 `TwelveDataPriceProvider` 没有 `@RateLimiter` / `@Retry`

`FinnhubNewsProvider:41-42` 和 `FinnhubPriceProvider:36-37` 都挂了
`@RateLimiter` + `@Retry`，`TwelveDataPriceProvider` 两个方法都是裸调用。

Twelve Data 免费档是 **8 req/min**，比 Finnhub 紧得多。
`QuoteRefreshService` 每分钟遍历整个 watchlist，Finnhub 一挂就整批打到 Twelve Data，
15 个 symbol 撞 8 req/min 的限额，后 7 个拿 429。

而且 `application.yml` 的 `resilience4j.ratelimiter.instances` 下只有
`finnhubNews` / `finnhubPrice` / `llmSentiment` 三个实例，没有 twelvedata 的。
建议加一个（`limit-for-period: 8`），然后在两个方法上挂
`@RateLimiter(name = "twelvedata")`。

`fetchDailyBars` 更要挂 —— 收盘快照一次性遍历全 watchlist，是最容易打爆配额的调用点。

### 3.2 `application.yml` 声明了 circuit breaker，全分支没有一处 `@CircuitBreaker`

`resilience4j.circuitbreaker.instances` 配了 `finnhub` 和 `llm` 两个实例，
`grep -c CircuitBreaker` 在 `backend/src/main` 下是 **0**。

CLAUDE.md 的 Resilience 行写着「Rate limit, retry, circuit breaker (decision 1)」，
三件里现在只有两件是真的。上游持续挂掉时没有熔断，
每一轮刷新都会把 15 个 symbol 各自重试 3 次（`externalApi` 是 `max-attempts: 3`），
也就是每分钟 45 次注定失败的请求 —— 这恰好是最容易被上游拉黑的行为模式。

不阻塞合入（重试次数有上限，不会雪崩），但**要么接上 `@CircuitBreaker(name = "finnhub")`，
要么把 yml 里那段改成注释说明「预留，当前未接线」**。
上一轮 §3.9 是同一类问题：配置声明了能力，代码没实现，而且不报错。

### 3.3 `ClosingSnapshotScheduler.isAfterClose` 是死代码

`scheduler/ClosingSnapshotScheduler.java:41-44`

```java
boolean isAfterClose(Instant now) {
    ZonedDateTime et = now.atZone(MARKET_ZONE);
    return et.getHour() >= 16;
}
```

package-private，没有任何调用点，也没有测试。cron 本身带 `zone` 已经保证了触发时刻，
这个方法不需要。删掉，或者如果是留给「手动触发时校验」用的，
那就现在接上并写个测试 —— 留着不用会让下一个人以为 cron 有二次校验。

对比一下 `QuoteRefreshScheduler.isTradingHours`：同样 package-private，
但有调用点、有 6 个测试。两者的差别就是「照可测性设计」和「写了忘了接」。


## 4. 关于 CI 与文档

**CI 的 secrets 接线（`ed6b649`）方向对，但和 CLAUDE.md 冲突了。**
`ci.yml` 的 `build` job 现在注入三个 secret：

```yaml
env:
  FINNHUB_KEY_NEWS: ${{ secrets.FINNHUB_KEY_NEWS }}
  FINNHUB_KEY_PRICE: ${{ secrets.FINNHUB_KEY_PRICE }}
  TWELVEDATA_API_KEY: ${{ secrets.TWELVEDATA_API }}
```

而 CLAUDE.md 写着「**CI needs no real API keys.** Finnhub is stubbed with WireMock」。
`build` job 只做 compose 校验 + `mvnw package`，不发真实请求，
所以真 key 其实不需要 —— `Seed placeholder env` 那步从 `.env.example` 填的占位值就够。
建议**删掉这三行**，让 CI 保持「不需要真 key」这个性质：一旦 CI 依赖真 key，
fork 上的 PR 会因为拿不到 secrets 而红，而且这条依赖不会有人记得。

如果保留是为了将来跑真实集成测试，请在 CLAUDE.md 里把那句话改掉，别让两处打对台。
顺带：secret 名 `TWELVEDATA_API` 和另两个 `_KEY_` 结尾的命名不一致，统一成 `TWELVEDATA_API_KEY`。

**两个 TEMP 文档要在合并前删掉。** 提交信息里自己写了「remove before merge」：

- `docs/TEMP-模块BC变更摘要-合并前移除.md`
- `docs/TEMP-第二轮修复-执行方案.md`

**`docker-compose.yml` 缺 `TWELVEDATA_API_KEY`。** 第 47-49 行只列了
`FINNHUB_KEY_NEWS` / `FINNHUB_KEY_PRICE` / `LLM_API_KEY` 三个必填项。
容器里 `twelvedata.key` 会取 `application.yml` 的默认空串，
于是 Twelve Data 这一路在 Docker 部署下静默失效 —— 而它现在是 `fetchDailyBars` 的**唯一**实现（§2）。
compose 里补一行 `TWELVEDATA_API_KEY: ${TWELVEDATA_API_KEY:-}` 即可
（用 `:-` 不用 `:?`，因为它有降级路径，不该阻止启动）。

**`.env.example` 的注释回退了一处。** 原来是
`price: finnhub | twelvedata | mock`，现在改成 `finnhub | mock`。
后者更准确（`twelvedata` 不是一个独立档位，是链里的第二跳），
但 `application.yml` 那行同步改了，两边一致，这条没问题 —— 记录一下免得下轮又当成漂移。
