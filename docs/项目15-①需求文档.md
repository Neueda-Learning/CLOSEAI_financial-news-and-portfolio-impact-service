# 1. 我们到底在做什么

## 1.1 一句话版本

> **用户输入自己持有哪些股票，系统自动抓这些公司的新闻，
> 判断每条新闻是好消息还是坏消息，再对比股价当天的实际涨跌，
> 告诉用户「这条新闻影响了你的哪几只股票、影响了多少钱」。**

## 1.2 说人话的版本

假设你持有苹果、英伟达、特斯拉。

平时你要自己去财经网站翻新闻，看到「英伟达财报超预期」，
你得自己想：这是好消息吧？我持有多少英伟达？今天涨了吗？涨的钱是多少？

我们做的系统把这四步全自动化了。

# 2. 术语表

先把词对齐，很多"懵"其实是因为同一个词大家理解不一样。

| 术语 | 意思 | 例子 |
|---|---|---|
| 组合 Portfolio | 用户的一个投资账户 | "我的美股账户" |
| 持仓 Holding | 组合里的一笔股票记录 | 持有 10 股 AAPL，均价 180 |
| 标的 Security | 一只股票本身的资料 | AAPL = Apple Inc.，纳斯达克 |
| 行情 / 报价 Quote | 股票当前价格 | AAPL 现价 $223.5 |
| 新闻 Article | 一条财经新闻 | "Nvidia beats Q2 estimates" |
| 情感分析 Sentiment | 判断一条新闻是好消息/坏消息 | 这条是正面，强度 0.7 |
| 影响评估 Impact | 一条新闻对某个持仓的具体影响 | 这条新闻让你的 NVDA 仓位涨了 $1600 |
| 外部 API | 别人提供的现成数据接口，我们调用它而不是自己造数据 | 某个财经数据服务商提供新闻和报价 |
| 归因日 | 一条新闻算在哪个交易日头上 | 收盘后的新闻算下一个交易日 |
| 一致性判定 | 新闻情感方向与股价实际方向是否吻合 | CONFIRMED / DIVERGENT / INCONCLUSIVE |

记住这几个词，后面所有内容都是这些概念的组合。
文档全文严格使用这里的词，不用同义词替换。

# 3. 完整例子：从头走一遍

假设系统已经建好，用户是"我"，走一遍真实场景。

**第一步，建组合和持仓。**
我打开系统，新建一个组合叫"美股账户"。加入三笔持仓：
- AAPL，10 股，成本 $180/股
- NVDA，20 股，成本 $100/股
- TSLA，5 股，成本 $250/股

**第二步，系统在后台自动干活（我不用管）。**
系统每隔一段时间，去查这三只股票有没有新新闻，查一下当前价格。
今天早上 12:31，系统抓到一条新闻：
"Nvidia beats Q2 estimates, raises guidance"（英伟达二季度业绩超预期，上调指引）

**第三步，系统判断这条新闻是好消息还是坏消息。**
系统读这条标题，判断：正面消息，强度 0.72（满分 1），置信度 0.88。

**第四步，系统对比股价实际动了多少。**
NVDA 昨天收盘 $121.40，新闻发布后价格涨到 $125.60，涨幅 4.15%。

**第五步，系统算出这条新闻对我的账户具体影响了多少钱。**
我持有 20 股 NVDA，这笔持仓占我账户总值的 30.3%。
- 这只股票本身：$121.40 → $125.60，涨了 $84（20 股 × $4.2）
- 系统的结论："这条新闻是正面消息，且股价确实涨了，方向一致，判定为'验证成功'"

**第六步，我在页面上看到什么。**
- 组合总览页：账户总值今天涨了多少
- 新闻列表：看到这条新闻，标着"正面"
- 点进这条新闻：左边是新闻标题，右边是 NVDA 当天的价格曲线，曲线上在 12:31 那个点打了个标记，旁边写着"+$84，方向验证成功"

这就是整个系统要做的全部事情。其余章节都是把这六步拆成可以分工开发的任务。

# 5. 业务规则

这一章是**开发前必须全组统一理解**的部分。规则不统一，代码就会各写各的。

## 5.1 组合估值规则

```
持仓市值   = 数量 × 当前价
持仓成本   = 数量 × 成本价
持仓盈亏   = 持仓市值 - 持仓成本
持仓权重   = 持仓市值 ÷ 组合总市值

组合总市值 = 所有持仓市值之和
组合当日涨跌 = Σ(数量 × (当前价 - 昨收价))
```

**举例**：20 股 NVDA，成本 $100，现价 $125.60
- 市值 = 20 × 125.60 = $2512
- 成本 = 20 × 100 = $2000
- 盈亏 = +$512（+25.6%）

## 5.2 情感分析规则

输出三个值：

| 字段 | 范围 | 含义 |
|---|---|---|
| label | POSITIVE / NEGATIVE / NEUTRAL | 方向标签 |
| score | -1 ~ 1 | 强度，-1 最负面，+1 最正面 |
| confidence | 0 ~ 1 | 有多确定 |

对这三个字段的要求：

- 同一条新闻用同一个引擎分析两次，结果必须完全一致（可复现）
- 无法判断时输出 NEUTRAL，不允许输出空值
- score 和 label 必须自洽：label 为 POSITIVE 时 score 必须大于 0

> **具体用什么算法算出这三个值，是实现选择，见架构文档决策 5。**
> 需求层面只约定输出契约，这样换引擎不需要改需求文档。

## 5.3 影响评估规则（最重要的一节）

### 先理解思路，再看公式

这个系统要回答的其实是**两个不同的问题**，容易混在一起：

| 问题 | 叫什么 | 数据来源 |
|---|---|---|
| 这条新闻**应该**影响哪些持仓、往哪个方向？ | **预期影响** | 新闻情感 + 持仓权重 |
| 股价**实际**动了多少、我账户实际赚亏多少钱？ | **实测影响** | 真实价格数据 |

**一定要拆成两条算，不要合成一个分数。**
因为最有价值的信息恰恰是"两者是否一致"—— 新闻说是好消息，股价真涨了吗？
这个一致性判断就是演示时最有说服力的东西。

### 公式

```
第一步：确定归因到哪一天
  归因日 d = publishedAt 所在交易日
  # 收盘后发布的新闻，归到下一个交易日

第二步：取四个输入
  情感 s     ∈ [-1, 1]      来自情感分析
  置信度 c   ∈ [0, 1]       来自情感分析
  持仓权重 w                 该持仓市值 ÷ 组合总市值
  价格变动 r = (当日收盘 - 前一日收盘) ÷ 前一日收盘
             # 盘中演示时用「最新报价 vs 前收盘」

第三步：算三个输出
  预期影响 expectedImpact  = s × c × w     # 有符号，回答「影响哪些持仓」
  实测贡献 observedContrib = w × r         # 该持仓拉动组合几个百分点
  金额影响 valueImpact     = 持仓市值 × r   # 演示时最直观的数字

第四步：判断一致性
  |r| < ε（默认 0.5%）  → INCONCLUSIVE   无法判断，波动太小是噪声
  s 和 r 同号           → CONFIRMED      验证成功，新闻方向与股价一致
  s 和 r 反号           → DIVERGENT      相反，新闻是好消息但股价跌了
```

> ε 做成配置项，方便演示前微调。

### 三个算例（拿这个写单元测试）

组合总市值 $128450.75。

**例 1 — CONFIRMED（演示要展示的就是这种）**

新闻："Nvidia beats Q2 estimates" → s = 0.72, c = 0.88
NVDA 持仓市值 $38900.25，权重 w = 0.303
昨收 $121.40 → 现价 $125.60，r = +4.15%

```
expectedImpact  = 0.72 × 0.88 × 0.303 = +0.192
observedContrib = 0.303 × 0.0415      = +1.258%
valueImpact     = 38900.25 × 0.0415   = +$1614.36
|r| = 4.15% > 0.5%，且 s > 0、r > 0 同号 → CONFIRMED
```

结论："这条正面新闻，股价确实涨了，你的账户多了 $1614"

**例 2 — DIVERGENT（说明模型不是万能的，诚实展示反而加分）**

新闻："Tesla announces new factory" → s = 0.55, c = 0.70
TSLA 权重 w = 0.12，r = -2.30%

```
expectedImpact  = 0.55 × 0.70 × 0.12 = +0.046   ← 预期利好
observedContrib = 0.12 × (-0.023)    = -0.276%  ← 实际下跌
s > 0 但 r < 0，反号 → DIVERGENT
```

结论："新闻看起来是利好，但股价反而跌了，可能有别的因素"

**例 3 — INCONCLUSIVE**

新闻："Apple updates App Store policy" → s = 0.20, c = 0.40
AAPL 权重 w = 0.328，r = +0.18%

```
|r| = 0.18% < 0.5% → INCONCLUSIVE
```

结论："股价基本没动，无法判断这条新闻有没有影响"

### 组合层面的日度汇总

```
加权情感   = Σ(s_i × c_i × w_i)          # 只统计当日有新闻的持仓
新闻覆盖率 = 有新闻的持仓数 ÷ 总持仓数
方向一致率 = CONFIRMED ÷ (CONFIRMED + DIVERGENT)
```

> **"方向一致率"这个指标强烈建议做。** 它等于在诚实量化自己模型准不准，
> 展示时说"我们的情感判断在 71% 的情况下与股价方向一致"，
> 比说"我们做了情感分析"专业得多。

## 5.4 新闻去重规则

**同一条新闻在系统里只能存在一份。** 无论定时任务重复跑多少次、
用户手动刷新多少次，已经抓过的新闻不得产生第二条记录。

判定依据：新闻源提供的外部唯一标识。

## 5.5 新闻与股票的关联规则

一条新闻可以关联多只股票（例如"芯片股集体大涨"同时影响多个持仓），
一只股票也可以有多条新闻。**这是多对多关系。**

关联必须准确：出现在某只股票下的新闻，必须确实是关于这家公司的。
宁可少关联，不可错关联 —— 错关联会直接毁掉演示的可信度。

> 关联的技术实现方式见架构文档决策 4，数据表怎么设计见架构文档 §4.3。

# 8. 边界条件与异常场景

**这一章是防 bug 的。每一条都必须有明确行为，"没想过"就等于线上崩溃。**
建议开发时逐条对照，测试时逐条覆盖。

## 8.1 空数据

| # | 场景 | 期望行为 |
|---|---|---|
| EC-01 | 组合里没有任何持仓 | 总市值显示 0，饼图显示空状态提示，不报错 |
| EC-02 | 持仓有了但一条新闻都没抓到 | 新闻列表显示"暂无新闻"，不显示空白页 |
| EC-03 | 有新闻但没有任何影响评估记录 | 影响页显示"暂无评估结果"及原因提示 |
| EC-04 | 系统里没有任何组合 | 引导用户创建第一个组合 |

## 8.2 无效输入

| # | 场景 | 期望行为 |
|---|---|---|
| EC-05 | 输入不存在的股票代码 | 明确提示"未找到该代码"，拒绝创建持仓 |
| EC-06 | 数量输入 0 或负数 | 校验拒绝，提示必须为正数 |
| EC-07 | 成本价输入 0 | **允许**（可能是赠股），但盈亏百分比显示为"—"而非除零错误 |
| EC-08 | 数量输入小数（如 0.5 股） | 明确规则：MVP 只接受整数股，校验拒绝 |
| EC-09 | 同一组合重复添加同一代码 | 明确规则：MVP 合并为一笔并重算加权均价 |
| EC-10 | 组合名为空或超长 | 校验拒绝，给出长度上限 |

## 8.3 外部数据异常

| # | 场景 | 期望行为 |
|---|---|---|
| EC-11 | 外部数据源超时或返回错误 | 用上次缓存数据，标注数据时间，记日志，不影响页面打开 |
| EC-12 | 外部数据源额度耗尽 | 同上，并在运维页面显示额度状态 |
| EC-13 | 某只股票停牌，查不到当前价 | 该持仓显示"无报价"，市值按最后已知价计算并标注 |
| EC-14 | 新闻缺少标题或时间字段 | 跳过该条，记日志，不入库 |
| EC-15 | 新闻返回的代码不在我们的持仓里 | 正常入库，但不生成影响评估 |

## 8.4 时间与交易日

| # | 场景 | 期望行为 |
|---|---|---|
| EC-16 | 新闻发布在收盘后 | 归到下一个交易日（§5.3 已定义） |
| EC-17 | 新闻发布在周末或假日 | 归到下一个交易日 |
| EC-18 | 缺少前一日收盘价，算不出涨跌幅 | 该条影响评估标为 INCONCLUSIVE，不硬算 |
| EC-19 | 新股上市不足两个交易日 | 同上 |

## 8.5 并发与一致性

| # | 场景 | 期望行为 |
|---|---|---|
| EC-20 | 定时任务和用户手动刷新同时触发 | 只跑一次；手动那次界面提示"正在刷新中"，不静默 |
| EC-21 | 用户在估值计算过程中删除了持仓 | 计算不崩溃，结果以删除后的状态为准 |
| EC-22 | 组合总市值为 0 时计算权重 | 权重全部显示 0 或"—"，不做除零运算 |
| EC-23 | 上一轮新闻拉取还没结束，下一轮已到点触发 | 跳过本轮并记日志，不重复拉取、不排队堆积 |
| EC-24 | 同一条新闻关联到组合里的多只持仓 | 为每个持仓各生成一条影响评估，互不覆盖 |

# 14. 建议的开发顺序

```
① 组合 + 持仓 CRUD                    ← 纯自有数据，最容易上手
② 接行情 API，算出市值和盈亏            ← 完成这步已满足 PDF 核心技术目标
③ 接新闻 API，抓取 + 去重 + 列表        ← 完成这步系统已可演示

⑤ 影响评估引擎
⑥ 联动视图 + 图表
⑦ 对外 API + Swagger + Docker + CI
```

> **关键判断：完成度 100% 的中等难度项目，出彩程度远高于 80% 的高难度项目。**
> 每完成一步都要保证系统是可运行、可演示的状态。
