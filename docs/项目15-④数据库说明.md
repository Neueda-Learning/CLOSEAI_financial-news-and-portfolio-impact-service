## 1. 先搞懂 Flyway 是什么

**Flyway 不是数据库，它和 MySQL 不是二选一。**

- **MySQL** 是数据库，数据存在那里
- **Flyway** 是迁移工具，把 `db/migration/` 下的 `.sql` 按版本号顺序执行到 MySQL 上，
  并在库里建一张 `flyway_schema_history` 记录「哪个脚本跑过了、校验和是多少」

Spring Boot 启动时 Flyway 自动扫 `backend/src/main/resources/db/migration/`，
发现没跑过的版本就执行。**你不需要手动进 MySQL 敲 `source xxx.sql`。**

为什么要它：五个人协作时，谁的库是什么状态不用靠群里喊。
你加了 V7 推上去，别人拉代码启动，V7 自动跑。

### 一条硬规则

> **已经提交的脚本，一个字都不能改。**

改一个字符校验和就变了，已经跑过那个版本的人下次启动会直接失败：

```
Migration checksum mismatch for migration version 1
```

要改表结构，**加一个新版本**（`V7__xxx.sql`），永远不要动 V1~V6。
这条没有例外，包括「我只是改了个注释」。

## 2. 怎么把库跑起来

### 路线 A：Docker（推荐，也是 CI 和演示用的路线）

```bash
cd financial-news-and-portfolio-impact-service
cp .env.example .env
# 编辑 .env，至少填 MYSQL_PASSWORD 和 MYSQL_ROOT_PASSWORD

docker compose up -d mysql
docker compose ps          # 等 STATUS 出现 (healthy)，约 30 秒

docker compose up backend  # 启动时 Flyway 自动跑 V1~V6
```

`docker-compose.yml` 会自动创建 `fnpis` 库和 `fnpis_user` 用户，字符集已配好 utf8mb4。

### 路线 B：本机已装 MySQL

```bash
mysql -uroot -p -e "CREATE DATABASE fnpis CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"

cd backend
MYSQL_USER=root MYSQL_PASSWORD=<你的密码> \
FINNHUB_KEY_NEWS=x FINNHUB_KEY_PRICE=x LLM_API_KEY=x \
./mvnw spring-boot:run
```

两点说明：

- `application.yml` 默认用户是 `fnpis_user`，本机 MySQL 用 root 的话必须显式传
  `MYSQL_USER=root`，否则连不上
- 那三个假 key 只为过启动时的占位符解析。三个密钥都**没有默认值**是故意的
  （架构 §7.5：默认值等于把 key 提交进仓库的风险敞口）。不做外部调用的模块随便填

### 启动成功的样子

```
Successfully validated 6 migrations
Migrating schema `fnpis` to version "1 - create core tables"
...
Successfully applied 6 migrations to schema `fnpis`, now at version v6
Started FnpisApplication in 4.787 seconds
```

### 验证

```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
SHOW TABLES;
SELECT COUNT(*) FROM security;
```

期望：六行且 `success` 全为 1、**10 张业务表**、`security` **15 行**。

## 3. 六个脚本分别做什么

| 脚本 | 建的表 | 谁在等这个脚本 |
|---|---|---|
| `V1__create_core_tables.sql` | `security`、`portfolio`、`holding` | 模块 A（组合持仓 CRUD） |
| `V2__create_news_tables.sql` | `news_article`、`article_security_link`、`sentiment_score` | 模块 C（新闻）、D（情感） |
| `V3__create_price_tables.sql` | `price_quote`、`price_bar` | 模块 B（行情） |
| `V4__create_impact_table.sql` | `impact_assessment` | 模块 E（影响评估） |
| `V5__seed_watchlist.sql` | 往 `security` 插 15 只大盘美股 | 模块 C 的轮询、模块 A 的代码校验 |
| `V6__create_valuation_snapshot.sql` | `portfolio_valuation_snapshot` | B5 / F5（价值走势图） |

顺序是**依赖顺序**：`security` 必须先于 `holding`（外键），
seed 必须晚于建表，`portfolio` 必须先于 `portfolio_valuation_snapshot`。

> V6 这张表**架构文档 §4.2 的表清单里没有**，但 §5 的收盘快照任务写「price_bar +
> 组合价值快照」，且 `valuation-history` 端点没有别的数据源，所以补上了。
> 架构文档 §4.2 需要同步。

## 4. 十张表分别干什么

「谁写」是指哪个模块负责往里插数据。**不是自己负责的表不要写入**，
需要数据就找对应模块要接口，否则两边各写一套就会打架。

### 核心实体（V1）

| 表 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `security` | 标的资料：代码 → 公司名。**同时就是 watchlist** —— 定时任务遍历这张表决定拉哪些股票的新闻和报价 | V5 seed（+ B 补公司名） | A 校验代码存在、C 轮询、前端搜索 |
| `portfolio` | 组合：一个投资账户，整个系统的根实体。估值、影响评估、快照都挂在它下面 | A | 全部模块 |
| `holding` | 持仓：组合里的一笔股票记录（代码、数量、成本价） | A | A 估值、B、E 算权重 |

**`holding` 里没有市值、盈亏、权重字段**，这三个都是读的时候用「数量 × 当前价」现算的。
不存冗余值的理由：价格一刷新，存下来的市值立刻就是错的。

### 新闻与情感（V2）

| 表 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `news_article` | 抓回来的每条财经新闻 | C | C 列表、D 分析、E 评估 |
| `article_security_link` | 新闻 ↔ 股票的关联。一条新闻可影响多只股票，一只股票有多条新闻，**多对多** | C | C 按代码筛选、E 找受影响持仓 |
| `sentiment_score` | 每条新闻的情感判定：标签 + 强度 + 置信度 | D | C 列表标签、E 取 s 和 c |

三点必须知道：

- **`news_article.external_id` 上的 UNIQUE 是整个去重机制的唯一依据**（C2、SC-005）。
  插入用 `INSERT ... ON DUPLICATE KEY UPDATE` 或先查再插，重复跑定时任务不会产生第二条
- **`article_security_link` 是独立表，不是 `news_article` 上的一个 symbol 字段。**
  架构 §4.3 点名这是最容易犯的建模错误，一条新闻影响多只股票时单字段存不下
- **`sentiment_score.article_id` 是 UNIQUE**，一篇一条。这个约束顺带保证同一条新闻
  不会被 LLM 重复分析（省钱）—— 用 upsert，任务重跑不产生额外 LLM 调用

### 行情（V3）

| 表 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `price_quote` | 最新报价，**每个代码只有一行**，原地更新。持仓现价、当日涨跌的来源 | B 报价刷新任务 | A 算市值、E 盘中算涨跌幅 |
| `price_bar` | 历史日线，每代码每交易日一行收盘价。**影响评估唯一的价格来源**，也是走势图数据源 | B 收盘快照任务 | E 算涨跌幅 r、F5 走势 |

`price_quote.as_of` 是**数据源的采集时间，不是我们写库的时间**。
所有响应里的 `asOf` / `stale` 都从它算出来，这是 SC-009 的验收点，别拿 `NOW()` 填。

`price_quote.previous_close` 可以为 NULL —— 新股上市不足两个交易日时算不出涨跌幅，
这种情况影响评估标 `INCONCLUSIVE`（EC-18/EC-19），不要硬填 0（会算出无穷大涨幅）。

### 影响评估（V4）

| 表 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `impact_assessment` | 一条新闻对一个持仓在一个归因日的影响：预期影响、实测贡献、金额影响、一致性判定 | E | E 列表、日度汇总、联动视图 |

**比率字段存的是比率，不是百分比。** `price_change_ratio = 0.0415` 对应契约里的
`priceChangePct: 4.15`，×100 只在 API 出口做一次。
两处都乘会得到 415%，这是最容易出的错。

**唯一键是 `(article_id, symbol, portfolio_id, attribution_date)` 四列。**
EC-24 要求一条新闻影响多个持仓时各生成一条记录，所以 symbol 必须在键里。
有这个键，`/impacts/recompute` 就能用 upsert 实现幂等；没有的话只能先 DELETE 再
INSERT，中途失败会在当日数据里留个洞。

**这张表故意不建外键到 `holding`。** 它记录的是「某条新闻对某个组合里某个代码的影响」，
不是对某一行持仓的影响。用户删掉一笔持仓（A6）不该连带删掉已经算出的历史评估 ——
演示时那些数据还要用。删整个组合会级联带走它，这是对的。

### 价值快照（V6）

| 表 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `portfolio_valuation_snapshot` | 每个组合每个交易日收盘时的总市值 | B 收盘快照任务 | F5 走势图 |

**这张表要尽早开始写数据。** 走势图要好几个交易日才画得出线，
架构 §6.3 的日线兜底方案也有同样的前置时间 —— 演示前一周补不出来。

## 5. 全库统一约定（写实体和 SQL 都要守）

这几条不统一，多人协作一定出问题。来源是架构 §4.4 和 §6.2。

| 项 | 约定 | 违反的后果 |
|---|---|---|
| 字符集 | 全库 `utf8mb4` / `utf8mb4_0900_ai_ci` | 新闻标题带 emoji 时**插入直接失败** |
| 金额、价格、数量 | MySQL `DECIMAL(18,4)` ／ Java `BigDecimal`，**禁止 `DOUBLE`/`double`** | `0.1+0.2=0.30000000000000004`，讲师手工验算对不上，砸掉 SC-002 |
| 比率、权重、涨跌幅 | `DECIMAL(10,6)`，存比率不存百分比 | 见上面 `impact_assessment` 那条 |
| 情感分值 | `DECIMAL(5,4)`，范围 -1~1 | — |
| 时间戳 | `DATETIME(3)` 存 **UTC** ／ Java `Instant`，**不用 `TIMESTAMP`** | `TIMESTAMP` 会按数据库时区自动转换，归因日算错（EC-16/EC-17） |
| 交易日 | `DATE` ／ `LocalDate` | — |
| 枚举 | 数据库存**字符串** `VARCHAR(24)`，Java 用 `@Enumerated(EnumType.STRING)` | 存序号的话，以后往枚举中间插一个值，历史数据全错 |
| 外部唯一 id | `VARCHAR(128)`，不要放大 | utf8mb4 下单列 UNIQUE 索引上限约 191 字符 |

枚举类已经在 `com.fnpis.domain` 下建好了，直接用，不要自己再定义一套：
`SentimentLabel`、`Direction`、`Alignment`、`MatchMethod`。

## 6. 写实体时的注意事项

`application.yml` 里 `spring.jpa.hibernate.ddl-auto: validate` 是开着的，
意思是：

> **实体字段和表结构对不上，应用直接启动失败，Hibernate 不会帮你改表。**

这是有意的（Flyway 独占 schema 所有权），但也意味着写 `@Entity` 时字段名、
`precision`/`scale`、`nullable` 必须逐个对齐 SQL。启动时报这类错就是漂移了：

```
Schema-validation: wrong column type encountered in column [quantity] in table [holding]
```

对齐示例：

```java
@Column(nullable = false, precision = 18, scale = 4)
private BigDecimal quantity;      // SQL: quantity DECIMAL(18,4) NOT NULL
```

各模块只写自己那几张表的实体。不是自己负责的表不要顺手也建一个 ——
两个人对同一张表建两个实体，Hibernate 缓存和事务边界都会出问题。

## 7. 以后要改表结构怎么办

**永远是加新版本，永远不改旧脚本。**

```
V7__add_note_to_holding.sql
V8__create_provider_status.sql
```

四条要求：

1. **版本号连续不重复。** 两个人同时开分支各写了一个 V7，合并时后合的那个改成 V8。
   合并前先看一眼 `db/migration/` 下最大的版本号是多少
2. **文件名格式** `V<数字>__<小写下划线描述>.sql`，两个下划线，少一个 Flyway 不认
3. **本地跑通再提 PR。** 起库、启动应用、看到 `Successfully applied N migrations`
4. **改了表就同步改实体**，否则 `ddl-auto: validate` 会让别人启动失败

如果本地库已经脏了（跑了一半失败、或手工改过表），最快的办法是重建：

```bash
docker compose down -v && docker compose up -d mysql    # -v 删掉 volume
```

本机 MySQL 的话 `DROP DATABASE fnpis;` 再重新 CREATE。
**不要手工 `DELETE FROM flyway_schema_history`** 去骗 Flyway，
那会让你的库和别人的库状态不一致，而且问题会在最难查的时候才暴露。

## 8. 集成测试

集成测试用 **Testcontainers 起真实 MySQL，不要用 H2**（架构 §7.2）。

H2 的 MySQL 兼容模式在 `DECIMAL` 精度、日期函数、唯一索引长度限制上和真 MySQL 有差异，
用 H2 测过的 Flyway 脚本在真 MySQL 上照样可能失败 —— 那就白测了。

依赖已经在 `pom.xml` 里了（`testcontainers:mysql` + `junit-jupiter`），
本地跑集成测试需要 Docker 在跑。CI 的 ubuntu runner 已预装 Docker，直接可用。

## 10. 三处与架构文档不一致，需要同步

| # | 情况 | 需要谁确认 |
|---|---|---|
| 1 | 补了 `portfolio_valuation_snapshot`（架构 §4.2 表清单没有，但 §5 的任务和 F5 端点都要它） | 架构文档维护者同步 §4.2 和 §4.5 |

| 3 | `impact_assessment` 加了四列 UNIQUE（§4.2 只写普通索引），为了让 recompute 幂等 | **模块 E 负责人确认** |

但新闻列表的 `asOf` 必须来自它 —— 用 `published_at` 算新鲜度会把一条昨天发布、
