## 1. 必须合入前修的（4 条）

### 1.1 `@Transactional` 实际不生效（自调用绕过代理）

| 位置 | |
|---|---|
| `service/NewsFetchService.java:62` | `fetchAll()` 里 `totalNew += fetchForSymbol(...)` |
| `service/NewsFetchService.java:69` | `@Transactional int fetchForSymbol(...)` |
| `service/QuoteRefreshService.java:71` | `refreshAll()` 里 `if (refreshOne(symbol))` |
| `service/QuoteRefreshService.java:79` | `@Transactional boolean refreshOne(...)` |

Spring 的 `@Transactional` 靠 AOP 代理生效。`fetchAll()` 用 `this.fetchForSymbol(...)`
直接调同类方法，调用不经过代理，注解不起作用。
`QuoteRefreshService.refreshAll()` → `refreshOne()` 同理。

`QuoteRefreshService` 的 Javadoc 现在写着：

> One symbol = one transaction. A failure on symbol N does not roll back symbols 1..N-1.

这句话目前不成立。实际行为是每个 `repository.save()` 各自跑在自己的隐式事务里
（Spring Data 的 `SimpleJpaRepository` 方法自带 `@Transactional`），
所以「不会整批回滚」这个结果碰巧是对的，但**理由完全不是注解**，
而且 `NewsFetchService` 那边少了一个真正需要的原子性：

```java
NewsArticle saved = articleRepo.save(article);          // 事务 1
linkRepo.save(new ArticleSecurityLink(saved.getId(),    // 事务 2
        symbol, MatchMethod.SYMBOL_EXACT));
```

两次 save 分属两个事务。第二次失败（连接断、超时）就留下一条
**有文章、没有 link** 的孤儿行。这行的下游后果落在 D/E 身上：

- D 会给它算情感（`sentiment_score` 只看 `news_article`），花掉一次 LLM 调用
- E 的 `article_security_link × holding` 相交为空，不产出评估
- 页面上表现为「有新闻、有情感、点进去没有影响评估」——
  这和 EC-15（新闻关联的股票不在持仓里）的表现**完全一样**，
  排查时根本分不清是数据缺陷还是正常边界

**修法（三选一，推荐第一个）：**

1. 把两个 `@Transactional` 方法挪到独立的 bean 里，由 `fetchAll` / `refreshAll` 注入调用。
   `NewsFetchService` 拆出 `NewsPersistenceService`，`QuoteRefreshService` 拆出
   `QuotePersistenceService`。最干净，也符合「service 只做业务规则」的分层。
2. 注入 `ApplicationContext` 或 self-proxy（`@Lazy NewsFetchService self`），
   调 `self.fetchForSymbol(...)`。改动小，但自引用代理这个手法要写注释解释，
   否则下一个人会觉得是笔误。
3. 用 `TransactionTemplate` 显式包住循环体。最直白，不依赖代理语义。

无论选哪个，**把 Javadoc 的那句承诺留着** —— 它描述的是正确的目标行为，
修完就成立了。

### 1.2 执行锁没锁住，EC-23 的重叠保护不存在

| 位置 | |
|---|---|
| `scheduler/NewsFetchScheduler.java:38` | `service.tryAcquire();` 返回值被丢弃 |
| `scheduler/QuoteRefreshScheduler.java:58` | 同上 |

```java
private void doFetch() {
    service.tryAcquire();      // ← 返回 boolean，没接
    try {
        service.fetchAll();    // ← 拿不到锁也照跑
    } finally {
        service.release();     // ← 把别人持有的锁放掉了
    }
}
```

两个后果，第二个更隐蔽：

1. **定时任务没有互斥。** `fixedDelay` 只保证同一个 `@Scheduled` 方法不自我重叠，
   它不阻止手动触发（HTTP 线程）和定时触发同时进 `fetchAll()`。
   CLAUDE.md 和 `application.yml` 的注释都把 EC-23 的保护归给 `fixedDelay`，
   但 EC-20 明确要求手动触发要有显式锁 —— 现在这个锁形同虚设。
2. **外层锁被内层放掉。** `manualFetch()` 先 `tryAcquire()` 成功，再调 `doFetch()`，
   `doFetch()` 的 `finally` 执行 `release()`，等它返回时锁已经是 false，
   `manualFetch()` 自己的 `finally` 再 release 一次（幂等，无害），
   但**在 `doFetch()` 返回之后、`manualFetch()` 返回之前的窗口里锁是开的**。
   更要紧的是：只要 `manualFetch` 在跑，`scheduledFetch` 进来后
   `doFetch` 里那句被忽略返回值的 `tryAcquire()` 拿不到锁，却继续执行了 `fetchAll()`,
   然后 `finally` 把手动那次的锁提前放掉。两次并发跑同一批 symbol，
   `findByExternalId` 的去重在两个事务里各自查空，双双 insert，
   最后靠 `uq_article_external_id` 抛约束异常 —— 表现为 500 而不是 409。

**修法：** 让 `doFetch` / `doRefresh` 只负责跑，锁在调用方获取，
统一成一个入口：

```
scheduledFetch():  if (!tryAcquire()) { log.debug("skipped, already running"); return; }
                   try { service.fetchAll(); } finally { release(); }
manualFetch():     if (!tryAcquire()) { throw ApiException.taskAlreadyRunning("news-fetch"); }
                   try { service.fetchAll(); } finally { release(); }
```

差别只在拿不到锁时的反应：定时任务跳过（正确 —— 轮询是幂等的，
排队只会在上游恢复时集中打爆限流器），手动触发返回 409。
这正是 CLAUDE.md「Scheduled Jobs」段落写的口径。

`ApiException.taskAlreadyRunning(String)` 用得对，`950da3a` 那次修正是对的，保留。

### 1.3 `TwelveDataPriceProvider.parseDatetime` 必然走兜底

`integration/twelvedata/TwelveDataPriceProvider.java:62-71`

```java
return Instant.parse(dt + "Z");
```

Twelve Data 的 `/quote` 返回的 `datetime` 是 `"2026-07-28 15:42:10"`
（空格分隔，不是 ISO-8601 的 `T`），而 `Instant.parse` 要求
`yyyy-MM-ddTHH:mm:ssZ`。拼一个 `Z` 上去改不了分隔符，
**每一次调用都会抛 `DateTimeParseException`，每一次都落到 `Instant.now()`**。

后果直接打在 D/E 最重要的那个接口上。`V7__create_price_point_table.sql`
对 `captured_at` 的列注释是：

> Provider capture time, never our write time. newsMarker is aligned onto this axis
> by the backend, so filling it with now() at write time shifts the annotation line
> away from where the price actually moved.

`impact-view` 的 `newsMarker`（演示当天那根新闻标注竖线）要对齐到这根轴上。
`captured_at` 全是写入时间的话，标注线会偏到价格实际变动之外的位置 ——
而这是整个项目「wow moment」的那一屏。

还有一层：Twelve Data 的 `datetime` 是**交易所本地时间**（US/Eastern），不带时区。
即使把分隔符修对，直接拼 `Z` 当 UTC 读也会差 4–5 小时。

**修法：**

```
DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss") → LocalDateTime
  → .atZone(ZoneId.of("America/New_York")).toInstant()
```

日线粒度的响应只有 `"2026-07-28"`（没有时间部分），所以要先试
`LocalDateTime`、失败再试 `LocalDate`，两个都不行才兜底。
兜底那一支请把 `log.warn` 保留并把原始字符串打出来 —— 现在这句写对了。

**顺带一条：** 兜底本身应该改成返回 `null` 而不是 `Instant.now()`，
让上层决定跳过还是补偿。理由见 §1.4 和 §3.1。

### 1.4 `c = 0` 拦不住，会写进 `price` 与 1970 的 `captured_at`

`integration/finnhub/FinnhubPriceProvider.java:44`

```java
if (r == null || r.c() == null) {
    return Optional.empty();
}
```

`FinnhubQuoteResponse.c` 是 `BigDecimal`，这个判断只能拦住**字段缺失**，
拦不住**字段为 0**。而 `t` 声明成 `long` 原语，缺失时 Jackson 填 0，
`Instant.ofEpochSecond(0)` 得到 `1970-01-01T00:00:00Z`。

于是当上游对某个代码返回全零对象（代码未知、停牌、免费档不覆盖，
这几种情况都可能得到一个 200 + 零值的 body），会发生：

- `price_quote.price` 写成 `0.0000`（列是 `NOT NULL DECIMAL(18,4)`，0 是合法值，进得去）
- `price_point` 插入一行 `(symbol, 1970-01-01T00:00:00Z, 0.0000)`
- `previous_close` 那行的 `> 0` 判断是对的，会存 null

对 D/E 的后果：E 从 `price_quote` 反推涨跌幅时会算出 `-100%`
（如果 `previous_close` 恰好还是上一次的有效值），或者拿到 0 分母。
1970 那行还会永久留在 `price_point` 里 —— V7 明确写了这张表没有清理任务，
且**这些行无法重新采集**。

**修法：** 判空改成判「不是一个有效价格」：

```
if (r == null || r.c() == null || r.c().signum() <= 0) → Optional.empty()
```

`t` 也一起：`t <= 0` 时 `capturedAt` 给 null，让 `QuoteRefreshService` 跳过
（配合 §3.1 的修法）。这个校验放在防腐层是对的位置 —— 上游的怪异格式
不该漏到 service。

## 3. 中低优先级（8 条）

### 3.1 写路径把 DB 缓存当兜底，成功计数虚高

`service/QuoteRefreshService.java:80` 用的是 `@Primary` 的 `ChainedPriceProvider`，
链尾是 `DbPriceProvider` —— 也就是**刷新任务在两个上游都失败时，
读自己上次写的缓存，再写回去**。

行本身无害（`price_quote` 主键覆盖、`as_of` 不变；`price_point` 的
`(symbol, captured_at)` 主键也是覆盖同一行），但 `refreshOne` 会为这个
symbol 返回 `true`，日志里 `Quote refresh complete: N/M symbols updated`
的 N 偏高 —— 上游整个挂掉时日志显示 15/15 全部成功，这是最需要告警的时刻。

**修法：** 写路径不该用带 DB 兜底的链。两个选择：
让 `QuoteRefreshService` 注入一个只含 Finnhub + Twelve Data 的链，
或者给 `QuoteSnapshot` 加一个 `source` 字段，`refreshOne` 见到 `DB` 就跳过并计入
「未更新」。前者更干净。

`DbPriceProvider` 本身留着是对的 —— 读路径（`GET /quotes`）需要它来实现
「上游挂了返回旧数据 + `stale: true`」，那是架构决策 2 的核心。
问题只在写路径复用了同一条链。

### 3.3 `LocalDate.now()` 用了服务器时区

`service/NewsFetchService.java:59`

```java
LocalDate today = LocalDate.now();
```

三个问题：不带 `Clock`（`QuoteRefreshScheduler` 已经注入了 `Clock` bean，
同一批代码两种做法）；用服务器默认时区，容器和笔记本结果不同；
不是市场时区。跨 UTC/ET 日界时那个 7 天窗口会整体平移一天，
CI 和本地拉到的新闻范围不一致。

改成 `LocalDate.now(clock)` 并注入 `Clock`，或者
`LocalDate.ofInstant(Instant.now(clock), ZoneId.of("America/New_York"))`。
`application.yml` 里 `connectionTimeZone=UTC` 那段注释讲的正是这个坑。

### 3.5 两种 bean 注入写法混用

```java
// FinnhubNewsProvider.java:29 —— 显式
FinnhubNewsProvider(@Qualifier("finnhubRestClient") RestClient restClient, ...)

// FinnhubPriceProvider.java:29 —— 靠参数名
FinnhubPriceProvider(RestClient finnhubRestClient, ...)

// TwelveDataPriceProvider.java:27 —— 靠参数名
TwelveDataPriceProvider(RestClient twelvedataRestClient, ...)
```

后两种依赖 `-parameters` 编译标志保留参数名（Spring Boot 的 parent POM
默认开着，所以现在能跑）。但有人加了个 `maven-compiler-plugin` 配置覆盖掉，
就会变成「两个 `RestClient` 候选、无法决定注入哪个」的启动失败 ——
而且报错信息不会指向这里。

统一成 `@Qualifier` 显式写，三处一致。

### 3.6 常量命名与位置

`integration/finnhub/FinnhubNewsProvider.java:76`

```java
private static final int NewsItemHeadlineMax = 512;
```

两处不规范：命名不是 `UPPER_SNAKE_CASE`（应为 `HEADLINE_MAX`），
声明在所有方法之后（Java 惯例是常量在类顶部）。
`backend/checkstyle.xml` 配置很轻，抓不到这条，但它在 `50` 行被引用、

### 3.7 `orElse` 应为 `orElseGet`

`service/QuoteRefreshService.java:94`

```java
PriceQuote q = quoteRepo.findById(symbol)
        .orElse(new PriceQuote(symbol, s.price(), s.previousClose(), s.capturedAt()));
```

`orElse` 的参数无条件求值，每次刷新都白构造一个 `PriceQuote`。
改 `orElseGet(() -> new PriceQuote(...))`。

这里还有个可读性问题：紧接着的四行又把 `price` / `previousClose` / `asOf`
全部 set 了一遍，所以构造器里传的三个值只有在「记录不存在」时短暂有效，
之后立刻被覆盖。写成 `orElseGet(() -> new PriceQuote(symbol, ...))` 后
建议构造器只传 `symbol`，其余交给下面的 setter，意图更清楚。

### 3.8 `NewsItem.summary` 取了但没用

`integration/NewsItem.java` 有 `summary`，`FinnhubNewsProvider` 也映射了它，

如果 D 后面想拿 `summary` 提升情感判断质量，那就是另一个话题，
需要先改需求范围 —— 现在不要为它加列。

### 3.9 `application.yml`：三个 provider 开关无人读取

`app.providers.news` / `price` / `sentiment` 三个 key，
整个分支里没有任何代码读它们（`ChainedPriceProvider` 用 `@Primary` 硬接，
`integration/mock/` 仍然只有 `.gitkeep`）。

但 `.env.example` 把它们列成了运维旋钮，架构 §8.1 更把
「演示当天翻到 mock」写成了 quota 耗尽时的后路。现在这条后路不存在 ——

mock 兜底是 quota 用尽时唯一的演示保障。

如果决定短期不做，请把注释改成「预留，当前未接线」，别让人以为能用。

整块注释掉了，提交信息里给的理由是对的：

> step-level exit 0 does not stop subsequent steps in GitHub Actions

这个诊断准确 —— step 级的 `if` 只作用于那一个 step，`exit 0` 让它成功结束后
`npm ci` 照样执行，`frontend/` 不存在就红。

注释掉能解决问题，但有个替代做法值得考虑：把 `if` 放回 **job 级别**。
job 级 `if` 为假时整个 job 显示 skipped，下游 `needs` 不会因此失败，
而且 `frontend/` 一落地就自动激活，不需要有人记得回来解注释。
CLAUDE.md 里 CI 表的「Conditional activation — jobs skip if code directory
doesn't exist yet」描述的就是这个行为。

现在这样也能跑，不阻塞合入。只是**请在 `frontend/` 落地时记得解注释** ——
注释掉的 job 不会在 checks 列表里出现，很容易一直忘。

## 附：D/E 侧与你有关的口径

- **不做美股假日表。** `QuoteRefreshScheduler.isTradingHours` 只排除周六周日，
  D/E 的 `AttributionDateResolver` 同样不查假日表。两个实现口径一致，
  这是好事 —— 代价是感恩节的新闻会归到感恩节，那天 `price_bar` 没有行，
  涨跌幅算不出来，结果是 `INCONCLUSIVE`。这是「说不准」而不是「算错了」，
  可以接受，是已知偏差不是待修 bug。
- **`ApiException.taskAlreadyRunning`** 我们的定时任务也会用同一个，
  不要改它的签名。
- **D/E 会复用你这四个 Repository**：`NewsArticleRepository`、
  `ArticleSecurityLinkRepository`、`PriceQuoteRepository`、`PricePointRepository`。
  缺的查询方法我们加在你的接口上，不另建第二个接口
  （`SecurityRepository` 的类注释定的规矩）。加方法时会在 PR 里 @ 你。
